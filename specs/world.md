# World

**Status:** Implemented

## Purpose

The World stores all data about the current interaction context — arbitrary deep-copyable registered values — for the rest of the system to read and react to. It serves two distinct roles:

1. **Shared state.** Any registered entry can be read (`get`) and reacted to (`add_listener`) by other modules, independent of the LLM entirely — e.g. bookkeeping, coordination state, or data one part of the system needs to hand to another.
2. **LLM-facing context.** Entries marked `include_in_prompt=True` also get rendered into **`Content`** (`render_full_prompt()`) — an ordered list of multimodal content parts (text, images, …) suitable for inclusion in an LLM prompt.

These roles are independent: an entry can be stored purely for other modules to consume — via listeners reacting to its updates — without ever being serialized into a prompt (`include_in_prompt=False`). `include_in_prompt` is the switch between the two: it doesn't control whether an entry is *stored* or *reactive*, only whether it's *shown to the model*.

The World holds current state only — a snapshot, not an event-sourced log of the Commands that produced it — and stores values directly, including multimodal data (e.g. images, audio), rather than by reference to an external blob store.

## Core concepts

### Keys

An entry is identified by a plain string `key` — the same string used to `register()` it, to look it up (`get`, `update`, ...), and the one that appears in the rendered prompt (`<entry key="...">`), so the model and any future Commands can reference it directly with no translation step.

### Registration and WorldEntryConfig

A key must be registered before any data can be stored under it — `register()` is how a key comes into existence in the World, and that call is where its static behavior/schema is defined: `type`, whether it reaches the LLM, whether it triggers a call, how it serializes, its TTL. This is captured in a `WorldEntryConfig`, set once at `register()` and unchanged until `unregister()` (there's no "reconfigure" API — changing behavior means unregistering and re-registering; re-registering an already-registered key raises `ValueError`, so `unregister()` first). Methods operating on a registered key (`get`, `update`, `get_entry`, `add_listener`, `unregister`) raise `KeyError` if the key isn't currently registered. `remove_listener` is the exception — it's a lenient, idempotent unsubscribe that no-ops on an unknown key or callback.

`register()` is generic over the entry's declared type (`register[T](key, type: type[T], *, serialize_fn: Callable[[T | None, T | None], Content], ...)`), so a mismatched `serialize_fn`/`archival_serialize_fn`/`trigger_condition_fn` is caught by a type checker right at the `register()` call site. Every other method (`get`, `update`, `get_entry`, `add_listener`, `remove_listener`, `unregister`) takes a plain `str` and works with `Any` values — there's no typed handle threading the declared type through the rest of the API. That's a deliberate scope decision. Carrying the declared type through every method via a typed key object — so that e.g. `get(key)` statically returns the right type — isn't worth its cost: pyright doesn't pin a shared `TypeVar` from one argument and strictly check the other, it solves for *any* type that satisfies both arguments jointly, which can silently widen away exactly the mismatch you'd want caught, and the payoff only lands when a type checker is actually running. Instead, `update()` validates every value against the entry's declared `type` **at runtime** (`TypeError` on mismatch, `None` always exempt) — the check that actually enforces type safety here, for every caller, tooling or not.

| Field | Description |
|---|---|
| `type` | Declared type of the stored value. `update()` validates new values against it and raises `TypeError` on mismatch (see `WorldEntryVersion.value` below for the `None` exemption). Validation is `isinstance`-based against a single declared class (`register`'s signature is `type[T]`) — a tuple of classes isn't accepted, and subscripted generics (`list[int]`, `dict[str, Any]`, …) aren't supported |
| `include_in_prompt` | Whether this entry is included when rendering the World prompt |
| `triggers_llm_call` | Whether updating this entry's value should trigger a new LLM call |
| `trigger_condition_fn` (optional) | Extra condition function evaluated on update; must pass, in addition to `triggers_llm_call`, for the update to actually trigger the LLM call. There's no automatic "skip if unchanged" behavior — `update()` never compares old vs. new value itself (equality is ambiguous or expensive for arbitrary types, e.g. images, and some entries legitimately want to re-trigger on an unchanged value, e.g. a heartbeat). If a no-op update shouldn't trigger, encode that here: `trigger_condition_fn=lambda old, new: old != new` |
| `serialize_fn` | Function that converts a value into **`Content`** (an ordered list of multimodal parts — see [content.md](content.md)) for the rendered prompt: `serialize_fn(value, previous_value)` (values only — does not receive the timestamp). Either argument may be `None` — because the entry was cleared/never set, or because there's no prior version yet. Receiving `previous_value` lets it phrase things differently depending on the transition (e.g. distinguishing "just cleared" from "never set"), especially around `None`. This is the **fresh** rendering — used when the entry is the current observation |
| `archival_serialize_fn` (optional) | Alternative serializer, same signature as `serialize_fn`, used when the entry is rendered as **history** (a past snapshot) rather than as the current/fresh observation; defaults to `serialize_fn` when omitted. Lets the registrant present a value one way when fresh and a lighter way once stale — e.g. an `ImagePart` inline while the image is current, but only a short `TextPart` description once it's historical, so heavy multimodal data isn't re-sent on every later turn. Which of the two a given render uses is chosen by the caller via `render_entry`'s `archival` flag; the *policy* for when an entry counts as archival lives in the Agent, not the World (see [agent.md](agent.md)) |
| `ttl` (optional) | Duration since the last update after which the value automatically resets to `None` via `update(key, None)`, if not refreshed before then. Enforced actively via a timer, not lazily on read; the timer restarts on every update that sets a non-`None` value. A TTL-driven reset behaves like `update(key, None)` in every respect — including advancing `id` like any other update (see `WorldEntryVersion` below) — except that it never triggers an LLM call even if `triggers_llm_call=True`. Each timer is bound to the specific version `id` it was armed for: if a newer `update()` advances the entry before the timer fires, the expiry is a no-op, so a TTL firing concurrently with a fresh update can never clobber the fresh value |
| `bypass_coalescing` (optional) | Whether an update to this entry should **skip the Agent's trigger-coalescing window** and start a step immediately, instead of waiting out the window for other triggers to join (see [agent.md](agent.md), "Trigger coalescing"). Defaults to `False`. Only meaningful together with `triggers_llm_call=True`. Like `triggers_llm_call` itself, this is a *declaration the World carries but does not act on*: the World copies it onto the `WorldEntry` snapshot (below) and the **Agent** enforces the coalescing policy — the same "World declares, Agent enforces" split as `serialize_fn`/`archival_serialize_fn` vs. the freshness *policy* (see [agent.md](agent.md)). It skips the *wait*, not the single-in-flight drop: a bypass update arriving while a call is already in flight is still dropped (barge-in/interruption is deferred — see [agent.md](agent.md)) |

### WorldEntryVersion

A single versioned snapshot of an entry's value — immutable once created; `update()` builds a new one rather than mutating an existing one in place:

| Field | Description |
|---|---|
| `id` | Identifier for this specific *version* of the entry's value: a small per-key incrementing integer (`1, 2, 3, ...`), assigned starting at `register()` and advancing by one on **every** subsequent `update()` call — including one that sets the value to `None` (an explicit clear or a TTL-driven reset). Clearing isn't special-cased: it's simply an update whose new value happens to be `None`, and it gets a new `id` like any other update. Included in the serialized output alongside `key` so the LLM (or a Command) can reference a specific entry/version — a mismatched `id` signals the data has changed since it was last seen, for *any* kind of change, clear included |
| `value` | The stored value (any deep-copyable type, including multimodal data — e.g. images, audio). `update()` deep-copies the supplied object before storing it, and World read/callback surfaces return defensive copies, so callers cannot mutate versioned state without another `update()` and its corresponding new id/timestamp/dispatch. `None` is always valid regardless of the declared `type` and clears the value; there's no separate `delete` |
| `timestamp` | Set when this version is created; used to order entries when rendering and stamped, in absolute form, onto the rendered entry |

`id` is a small per-key incrementing integer rather than a UUID/hash: any reference to an entry always pairs `id` with `key`, so global uniqueness isn't needed, and small integers are far easier for a model to reproduce exactly than a hex string. It is always a plain, positive integer — there is no "no version yet" state, since `register()` itself assigns `id=1` to the entry's initial (empty) version.

### Value ownership and defensive copies

The World has **value semantics**, not shared-reference semantics. Values must be deep-copyable. `update()` copies on ingress; `get()`, `get_entry()`, `get_prompt_entries()`, listener dispatch, and `on_trigger` return or emit copies; and serializers/trigger conditions receive copies. This is what makes an id a trustworthy version marker: retaining the object passed to `update()`, mutating a getter result, or mutating a callback payload cannot silently change live state behind the World's lock without advancing the id. Immutable values such as strings and bytes are naturally cheap to copy.

The counter for each key lives in a dictionary separate from the live entries and is never cleared — so after `unregister()`/re-`register()`, the entry's fresh initial version (created by `register()` itself) picks up the next integer past the last one that key ever had, rather than restarting at 1 (which would let a stale old reference collide with a reused `id`).

### WorldEntry

The live state for a registered key — created by `register()` and updated by every `update()`:

| Field | Description |
|---|---|
| `key` | Stable identifier for this entry's slot in the World (dictionary key); unchanged across updates |
| `type` | Declared type of the stored value, copied from the `WorldEntryConfig` set at `register()` — carried on `WorldEntry` too so a snapshot of it (e.g. handed to a listener/trigger-handler callback) is self-describing without a separate config lookup. Unlike `current`/`previous` below, this never changes across updates, so it isn't duplicated per version |
| `bypass_coalescing` | Whether updates to this entry skip the Agent's coalescing window, copied from the `WorldEntryConfig` set at `register()` — carried on `WorldEntry` for the same reason as `type`: so the snapshot handed to the trigger handler is self-describing and the Agent can honor the flag without a config lookup. Like `type`, it never changes across updates |
| `current` | The entry's current `WorldEntryVersion` |
| `previous` | The `WorldEntryVersion` immediately before `current`, or `None` in the brief window between `register()` and the first `update()`. Exists so `serialize_fn` can react to the transition (e.g. rendering a cleared value differently from a never-set one) without the World keeping a full history — just one step back, consistent with the World being snapshot-based rather than event-sourced |

`register()` creates `current = WorldEntryVersion(id=1, value=None, timestamp=<register time>)` and `previous = None` — registration itself produces the entry's first version, not a version-less placeholder. Every `update()` shifts the old `current` into `previous` and builds a fresh `current`, with `id` one greater than the previous version's `id`, regardless of whether the new value is `None` or not.

### World API

The World is a **plain instantiable class**, constructed with the asyncio event **loop** it dispatches callbacks on (`World(loop)`) and owned by the `Wica` facade (see [wica.md](wica.md)) — `Wica.init` creates one loop, constructs one `World(loop)` per instance, and hands the World out as `wica.world`. It is **not a global singleton**: each `Wica` owns exactly one World, reached through it rather than through a module-level accessor, and "reset the World" is expressed by closing the `Wica` and building a new one (see [wica.md](wica.md), "Reset is recreation"). Tests construct a `World(loop)` directly and manage its lifecycle with `start()`/`stop()` (below) for isolation.

### The shared event loop

The World does **not** own a thread pool of its own. It is handed an asyncio event **loop** at construction — the *same* loop the Agent runs on, owned and run by the `Wica` facade in one daemon thread (see [wica.md](wica.md), "Lifecycle"; [agent.md](agent.md), "The shared event loop"). All of the World's reactive dispatch (per-key listeners and the `on_trigger` Event) is scheduled onto that shared loop, so the whole system has **one background execution context with a single owner**, instead of the World owning an executor and the Agent owning a separate loop with a bridge between them. `update()` may still be called from **any thread** (sensor/hardware/UI producers): it reaches the loop with `loop.call_soon_threadsafe(...)`, so the from-any-thread property is preserved — only the *dispatch* runs on the loop.

An update has **two reactive outputs**, both scheduled onto the loop and both fire-and-forget (neither blocks `update()`'s caller):

**Per-key listeners (`add_listener`) — loop-aware, sync/async, parallel, isolated.** A listener may be a plain **sync** function or an **async** coroutine function, and the World dispatches each on the shared loop accordingly (detected via `asyncio.iscoroutinefunction`):

- an **async** listener → scheduled as a task on the loop (`loop.create_task`), interleaving cooperatively at each `await`.
- a **sync** listener → offloaded to the loop's default thread-pool executor (`loop.run_in_executor(None, …)`), so a **blocking** sync listener runs on a worker thread and never stalls the loop. Multiple sync listeners land on multiple worker threads — **parallel**.

Each listener is scheduled **independently** and **individually guarded** (the async branch wraps the coroutine in `try/except`; the sync branch retrieves its future's exception in a done-callback) — an exception is **caught and logged, never propagated and never allowed to starve siblings**. This closes the earlier gap where a listener exception failed silently. (The thread pool is just a helper the loop offloads blocking work to — the standard asyncio pattern — not a dispatch path the World owns and must lifecycle; the loop's default executor is torn down with the loop, by `Wica`.)

**The trigger — the `on_trigger` Event.** When an update qualifies to wake the agent (`triggers_llm_call` set and any `trigger_condition_fn` passes), the World emits its **`on_trigger: Event[WorldEntry]`** (see [events.md](events.md)) — scheduled on the loop via `call_soon_threadsafe(self.on_trigger.emit, entry)` so subscribers run on the loop thread. The Agent is **just a subscriber** — it attaches a one-line sync shim that `create_task`s its async `_handle_trigger` (see [agent.md](agent.md), "The shared event loop") — and any number of other observers (e.g. a UI showing raw inputs) may subscribe too. `Event.emit`'s per-subscriber isolation guards each one. Note `on_trigger` is the **raw** signal: it fires on *every* qualifying update, *before* the Agent's coalescing/single-in-flight logic, so it includes triggers the Agent may later drop. The Agent's own **filtered** view — fired only for triggers a step actually processed — is a separate `agent.on_trigger` Event (see [agent.md](agent.md), "Instrumentation"); `Wica` surfaces both, disambiguated as `on_world_trigger` and `on_agent_trigger` (see [wica.md](wica.md)).

### Lifecycle: `start()` / `stop()` and `is_running`

The World has a symmetric **`start()`/`stop()`** lifecycle mirroring the Agent's, so the `Wica` facade drives both together (start World→Agent, stop Agent→World — see [wica.md](wica.md), "Lifecycle"). Because the loop itself is owned and run by `Wica`, the World's own `start()`/`stop()` are **light** — they gate the reactive path and clean up timers; they do **not** create or tear down the loop or any thread pool:

- **`start()`** sets `is_running = True` and restores TTL timers for retained non-`None` values. The deadline remains the original update timestamp plus the configured TTL; if it passed while stopped, the value resets immediately on restart (with ordinary listener dispatch but, like every TTL reset, no LLM trigger).
- **`stop()`** atomically sets `is_running = False`, detaches all outstanding TTL timers, then cancels them. This closes the race in which a concurrent update could otherwise arm a timer during teardown.
- **`is_running`** is a read-only flag exposing the state.

**Only the reactive path is guarded.** `update()` (and its internal `_update`) raise `RuntimeError("World is not running")` when the World isn't running — it's the operation that dispatches onto the loop, and the one that's dangerous once torn down. Everything else — `register`, `unregister`, `get`, `get_entry`, `get_prompt_entries`, `add_listener`, `remove_listener`, subscribing to `on_trigger`, `render_entry`, `render_full_prompt` — is **unguarded**: these only mutate dicts under the lock or read state, so they need no running loop. This is a deliberate split: `start()`/`stop()` gate the *reactive dispatch*, not the *data model*, so the natural **setup-before-start** flow keeps working — register entries (and let the Agent register commands) on a not-yet-started World, then `start()` turns on the flow. Reads on a stopped World return stale state rather than raising (a held `wica.world` reference is still safely inspectable after `stop()`); it's the mutating `update()` that fails fast. Registered entries and values persist across every supported `stop()`/`start()` pause; TTL time continues to elapse while stopped and is reconciled by the next `start()`.

Internally, the World holds two parallel per-key stores: registration metadata (`WorldEntryConfig`) and live state (`WorldEntry`), both keyed by the plain string `key`. Keeping registration and live state apart means callback snapshots copy the entry and its value, but never the serializer/condition callables living in `WorldEntryConfig`.

The World exposes the following API:

- `start()` / `stop()` — restartable lifecycle bookends (see "Lifecycle" above). `start()` sets `is_running` and restores retained TTL deadlines; `stop()` atomically clears `is_running` and cancels timers. Both are light: the shared event loop is owned and run by `Wica`, not the World. Driven by the `Wica` facade alongside the Agent's own `start()`/`stop()`
- `is_running` — read-only flag; `True` between `start()` and `stop()`
- `register(key, type, ...)` — registers a new entry: stores its `WorldEntryConfig` and creates its initial `WorldEntry` (`current` version `id=1`, `value=None`); can happen at any time, including mid-run, and **does not require the World to be running** (part of the setup-before-`start` flow — see "Lifecycle"). Generic over the declared type (see "Keys" above) — the one place in this API a type checker verifies anything about it. Returns nothing; the caller already has the `key` string it passed in
- `unregister(key: str)` — removes an entry entirely (its `WorldEntryConfig`, its `WorldEntry`, and any listeners registered for that key are all gone); never triggers an LLM call, even if the entry had `triggers_llm_call=True`
- `update(key: str, value: Any)` — validates and deep-copies `value` into World-owned state, shifts the entry's current version into `previous`, and builds a new current version (new timestamp; `id` one greater than the previous version's, always — see `WorldEntryVersion` above). It evaluates the trigger condition over defensive copies and (currently) triggers an LLM call whenever `triggers_llm_call` is set and the condition passes. **Requires the World to be running** — the sole guarded method (see "Lifecycle"): called before `start()` or after `stop()` it raises `RuntimeError("World is not running")`, since it dispatches onto the loop and must fail fast rather than touch a torn-down World. Validates `value` against the entry's declared `type` at runtime (`TypeError` on mismatch, `None` always exempt) — the check that actually enforces type safety here. Clearing a value (without unregistering) is just `update(key, None)` — there's no separate `delete`. Schedules the trigger handler and any listener callbacks onto the shared loop (`call_soon_threadsafe`) rather than running them inline, so a slow callback (e.g. the trigger handler making an actual LLM call) never blocks the caller — each is then run sync-on-the-pool or async-on-the-loop and individually guarded (see "The shared event loop"). Every callback receives its own defensive `WorldEntry` snapshot, so neither a later update nor callback-side mutation can rewrite live state
- `get(key: str) -> Any` — returns a defensive copy of the current value stored for a key
- `get_entry(key: str) -> WorldEntry` — returns a defensive copy of the entry's full current `WorldEntry` (both `current` and `previous` versions), not just the value — primarily so a caller can pass it to `render_entry` (below)
- `get_prompt_entries() -> list[WorldEntry]` — returns defensive copies of the current `WorldEntry` for every `include_in_prompt` entry, ordered by timestamp: the same selection `render_full_prompt()` computes internally, but handed back as raw entries rather than pre-rendered `Content`, so a caller can apply its own per-entry fresh/archival choice at render time instead of one being baked in at capture time. Added to support the Agent's per-trigger history snapshot (see [agent.md](agent.md) "History") capturing the full included World state, not only the entry that fired
- `add_listener(key: str, callback)` / `remove_listener(key: str, callback)` — subscribe/unsubscribe a callback invoked whenever the entry at `key` is updated, dispatched on the shared loop alongside the trigger handler (see `update()` and "The shared event loop") rather than synchronously within `update()`. The callback may be **sync** (`Callable[[WorldEntry], None]`, offloaded to the loop's thread pool) or **async** (`Callable[[WorldEntry], Awaitable[None]]`, run as a loop task). Each callback receives an independent defensive snapshot. Dispatch is fire-and-forget, but no longer silent-on-error: each callback is individually guarded, so an exception it raises is **caught and logged**, isolated from `update()`'s caller, from the loop, and from sibling callbacks
- `on_trigger: Event[WorldEntry]` — the World's trigger signal (see "The shared event loop"), emitted when an update qualifies to wake the agent (`triggers_llm_call` set and any `trigger_condition_fn` passes), one signal for the entire World carrying the entry that fired regardless of its declared type. Subscribers attach with `world.on_trigger.subscribe(...)`, so the Agent is one subscriber (via an async-scheduling shim — see [agent.md](agent.md), "The shared event loop") and observers like a UI can subscribe alongside it. Emitted on the loop thread (`call_soon_threadsafe`) so a subscriber may safely `create_task`; `Event`'s per-subscriber isolation guards each. The **raw**, pre-coalescing signal — the Agent's filtered counterpart is `agent.on_trigger`
- `render_entry(entry: WorldEntry, *, archival: bool = False, serialize_fn: Callable[[Any, Any], Content] | None = None) -> Content` — serializes a `WorldEntry` snapshot into the XML-style block described below as `Content` (parts), *regardless* of that entry's `include_in_prompt` — an explicit per-entry request bypasses the aggregate-prompt filter, since the caller (e.g. a trigger handler wanting just the entry that fired, rather than the whole World) is asking for this entry specifically. `archival=False` (default) uses `serialize_fn`; `archival=True` uses `archival_serialize_fn` (which itself falls back to `serialize_fn`). An explicit `serialize_fn` argument overrides the registered one and skips the config lookup entirely, so a caller can still render an entry whose key has since been `unregister()`ed (e.g. the Agent re-rendering a retired command entry from a history snapshot after the World has dropped its config — see [agent.md](agent.md)); the `<entry …>` envelope below stays owned by the World either way. Takes the `WorldEntry` itself, not a key, so it renders exactly the snapshot the caller is holding (e.g. one already received via a listener/trigger-handler callback, or fetched via `get_entry`) rather than re-reading whatever the World's live state happens to be at render time — the two can otherwise diverge if another `update()` lands in between the caller obtaining the entry and rendering it
- `render_full_prompt() -> Content` — serializes all `include_in_prompt` entries into a single `Content`, ordered by timestamp, by calling `render_entry(entry)` (fresh) for each and concatenating the parts

`render_full_prompt()` renders all currently included entries. `render_entry(entry)` is the lower-level building block used by the Agent's snapshot-history renderer, which decides fresh versus archival rendering for each observation.

### Rendered entry format

Each entry — whether from `render_entry(entry)` or as part of `render_full_prompt()` — is wrapped in an XML-style tag, chosen because Claude tracks tag boundaries and attribute values reliably — both reading them and echoing them back precisely, which matters since the model may need to reference a `key`/`id` exactly (e.g. in a Command). Because rendering now yields `Content` (parts) rather than a string, the wrapper is expressed as `TextPart`s **bracketing** the serialized parts: an opening `TextPart` (`<entry ...>\n`), then the parts returned by the (fresh or archival) serialize function, then a closing `TextPart` (`\nUpdated: ...\n</entry>\n`). The closing part's **trailing newline** makes each entry self-separating: when entries are concatenated (the way adjacent parts merge — see [content.md](content.md)), each `</entry>` lands on its own line and the next `<entry ...>` starts on the following line, so blocks never glue together (`</entry><entry ...>`) and no separator part is needed between them. For a text-only entry this flattens to exactly the block below; for a multimodal one the image sits as its own part between the two text parts (the Agent's adapter may merge adjacent `TextPart`s when converting to provider blocks):

```
<entry key="user_profile" id="1">
Jane is logged in as an administrator, currently editing the billing page.
Updated: 2026-07-20T14:32:10Z
</entry>
```

- **Prefix** (opening tag attributes, in the opening `TextPart`): `key` and `id` — structured and unambiguous, cheap for the model to copy verbatim. `id` is always present: `register()` itself assigns `id=1` to an entry's initial (empty) version, so there is no "no version yet" state that would otherwise need special-casing out of the tag.
- **Content**: the untouched parts returned by `serialize_fn` (fresh) or `archival_serialize_fn` (archival).
- **Trailing line** (in the closing `TextPart`, after the content): a plain `Updated: <ISO 8601 timestamp>` line, deliberately not an attribute — visually separating stable identity (`key`/`id`, referenceable) from freshness (informational only), while staying structurally inside `<entry>...</entry>` so its association with this entry (and not a neighboring one) is unambiguous rather than relying on line ordering. The timestamp is always **absolute**, never relative phrasing ("updated 5s ago"): once text is sent to the LLM it's frozen, so a pre-rendered relative time would silently go stale as soon as that message sits in history (or a cached prompt prefix) longer than the phrasing implies. If recency framing is wanted, it's the model's job at inference time, informed by a small "current time" marker injected fresh outside the cached/stable part of the prompt on each call — not stored on the entry or persisted into history.

`render_full_prompt()` concatenates these blocks' parts, one per included entry (each produced by `render_entry(entry)`), in timestamp order, into a single `Content` — relying on each block's trailing newline to separate adjacent entries rather than inserting its own separator part.

## Open questions

1. **Stale-`id` handling** — what happens when something (e.g. a Command) references an `id` that no longer matches the entry's current `id`? Since `id` now advances on *every* `update()` — including a mere clear or a TTL reset, not only a genuinely new value — a stale reference becomes detectable after any change to the entry, not just a replacement. The World doesn't expose anything like `get_by_id(key, id)` to look up a specific historical version (it only ever keeps `current`/`previous`, never a full history); the actual mismatch-handling behavior is likely primarily a Commands-spec concern (see [commands.md](commands.md) open question #3).
