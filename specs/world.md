# World

**Status:** Draft

## Purpose

The World stores all data about the current interaction context — arbitrary registered objects — for the rest of the system to read and react to. It serves two distinct roles:

1. **Shared state.** Any registered entry can be read (`get`) and reacted to (`add_listener`) by other modules, independent of the LLM entirely — e.g. bookkeeping, coordination state, or data one part of the system needs to hand to another.
2. **LLM-facing context.** Entries marked `include_in_prompt=True` also get rendered into **`Content`** (`render_full_prompt()`) — an ordered list of multimodal content parts (text, images, …) suitable for inclusion in an LLM prompt.

These roles are independent: an entry can be stored purely for other modules to consume — via listeners reacting to its updates — without ever being serialized into a prompt (`include_in_prompt=False`). `include_in_prompt` is the switch between the two: it doesn't control whether an entry is *stored* or *reactive*, only whether it's *shown to the model*.

The World holds current state only — a snapshot, not an event-sourced log of the Commands that produced it — and stores values directly, including multimodal data (e.g. images, audio), rather than by reference to an external blob store.

## Core concepts

### Keys

An entry is identified by a plain string `key` — the same string used to `register()` it, to look it up (`get`, `update`, ...), and the one that appears in the rendered prompt (`<entry key="...">`), so the model and any future Commands can reference it directly with no translation step.

### Registration and WorldEntryConfig

A key must be registered before any data can be stored under it — `register()` is how a key comes into existence in the World, and that call is where its static behavior/schema is defined: `type`, whether it reaches the LLM, whether it triggers a call, how it serializes, its TTL. This is captured in a `WorldEntryConfig`, set once at `register()` and unchanged until `unregister()` (there's no "reconfigure" API — changing behavior means unregistering and re-registering; re-registering an already-registered key raises `ValueError`, so `unregister()` first). Methods operating on a registered key (`get`, `update`, `get_entry`, `add_listener`, `unregister`) raise `KeyError` if the key isn't currently registered. `remove_listener` is the exception — it's a lenient, idempotent unsubscribe that no-ops on an unknown key or callback.

`register()` is generic over the entry's declared type (`register[T](key, type: type[T], *, serialize_fn: Callable[[T | None, T | None], Content], ...)`), so a mismatched `serialize_fn`/`archival_serialize_fn`/`trigger_condition_fn` is caught by a type checker right at the `register()` call site. Every other method (`get`, `update`, `get_entry`, `add_listener`, `remove_listener`, `unregister`) takes a plain `str` and works with `Any` values — there's no typed handle threading the declared type through the rest of the API. That's a deliberate scope decision: an earlier draft tried carrying the declared type through every method via a typed key object, but keeping that genuinely useful past `register()` (e.g. having `get(key)` statically return the right type) turned out to need real care — pyright doesn't pin a shared `TypeVar` from one argument and strictly check the other, it solves for *any* type that satisfies both arguments jointly, which can silently widen away exactly the mismatch you'd want caught. That complexity bought a benefit that only helps when a type checker is actually running. Instead, `update()` validates every value against the entry's declared `type` **at runtime** (`TypeError` on mismatch, `None` always exempt) — the check that actually enforces type safety here, for every caller, tooling or not.

| Field | Description |
|---|---|
| `type` | Declared type of the stored value. `update()` validates new values against it and raises `TypeError` on mismatch (see `WorldEntryVersion.value` below for the `None` exemption). Validation is `isinstance`-based against a single declared class (`register`'s signature is `type[T]`) — a tuple of classes isn't accepted, and subscripted generics (`list[int]`, `dict[str, Any]`, …) aren't supported |
| `include_in_prompt` | Whether this entry is included when rendering the World prompt |
| `triggers_llm_call` | Whether updating this entry's value should trigger a new LLM call |
| `trigger_condition_fn` (optional) | Extra condition function evaluated on update; must pass, in addition to `triggers_llm_call`, for the update to actually trigger the LLM call. There's no automatic "skip if unchanged" behavior — `update()` never compares old vs. new value itself (equality is ambiguous or expensive for arbitrary types, e.g. images, and some entries legitimately want to re-trigger on an unchanged value, e.g. a heartbeat). If a no-op update shouldn't trigger, encode that here: `trigger_condition_fn=lambda old, new: old != new` |
| `serialize_fn` | Function that converts a value into **`Content`** (an ordered list of multimodal parts — see [content.md](content.md)) for the rendered prompt: `serialize_fn(value, previous_value)` (values only — does not receive the timestamp). Either argument may be `None` — because the entry was cleared/never set, or because there's no prior version yet. Receiving `previous_value` lets it phrase things differently depending on the transition (e.g. distinguishing "just cleared" from "never set"), especially around `None`. This is the **fresh** rendering — used when the entry is the current observation |
| `archival_serialize_fn` (optional) | Alternative serializer, same signature as `serialize_fn`, used when the entry is rendered as **history** (a past snapshot) rather than as the current/fresh observation; defaults to `serialize_fn` when omitted. Lets the registrant present a value one way when fresh and a lighter way once stale — e.g. an `ImagePart` inline while the image is current, but only a short `TextPart` description once it's historical, so heavy multimodal data isn't re-sent on every later turn. Which of the two a given render uses is chosen by the caller via `render_entry`'s `archival` flag; the *policy* for when an entry counts as archival lives in the Agent, not the World (see [agent.md](agent.md)) |
| `ttl` (optional) | Duration since the last update after which the value automatically resets to `None` via `update(key, None)`, if not refreshed before then. Enforced actively via a timer, not lazily on read; the timer restarts on every update that sets a non-`None` value. A TTL-driven reset behaves like `update(key, None)` in every respect — including advancing `id` like any other update (see `WorldEntryVersion` below) — except that it never triggers an LLM call even if `triggers_llm_call=True`. Each timer is bound to the specific version `id` it was armed for: if a newer `update()` advances the entry before the timer fires, the expiry is a no-op, so a TTL firing concurrently with a fresh update can never clobber the fresh value |

### WorldEntryVersion

A single versioned snapshot of an entry's value — immutable once created; `update()` builds a new one rather than mutating an existing one in place:

| Field | Description |
|---|---|
| `id` | Identifier for this specific *version* of the entry's value: a small per-key incrementing integer (`1, 2, 3, ...`), assigned starting at `register()` and advancing by one on **every** subsequent `update()` call — including one that sets the value to `None` (an explicit clear or a TTL-driven reset). Clearing isn't special-cased: it's simply an update whose new value happens to be `None`, and it gets a new `id` like any other update. Included in the serialized output alongside `key` so the LLM (or a Command) can reference a specific entry/version — a mismatched `id` signals the data has changed since it was last seen, for *any* kind of change, clear included |
| `value` | The actual stored object (any type, including multimodal data — e.g. images, audio). `None` is always a valid value here regardless of the entry's declared `type` — exempt from the type-check that otherwise raises on mismatch. This is also how a value gets cleared; there's no separate `delete` |
| `timestamp` | Set when this version is created; used to order entries when rendering and stamped, in absolute form, onto the rendered entry |

`id` is a small per-key incrementing integer rather than a UUID/hash: any reference to an entry always pairs `id` with `key`, so global uniqueness isn't needed, and small integers are far easier for a model to reproduce exactly than a hex string. It is always a plain, positive integer — there is no "no version yet" state, since `register()` itself assigns `id=1` to the entry's initial (empty) version.

The counter for each key lives in a dictionary separate from the live entries and is never cleared — so after `unregister()`/re-`register()`, the entry's fresh initial version (created by `register()` itself) picks up the next integer past the last one that key ever had, rather than restarting at 1 (which would let a stale old reference collide with a reused `id`).

### WorldEntry

The live state for a registered key — created by `register()` and updated by every `update()`:

| Field | Description |
|---|---|
| `key` | Stable identifier for this entry's slot in the World (dictionary key); unchanged across updates |
| `type` | Declared type of the stored value, copied from the `WorldEntryConfig` set at `register()` — carried on `WorldEntry` too so a snapshot of it (e.g. handed to a listener/trigger-handler callback) is self-describing without a separate config lookup. Unlike `current`/`previous` below, this never changes across updates, so it isn't duplicated per version |
| `current` | The entry's current `WorldEntryVersion` |
| `previous` | The `WorldEntryVersion` immediately before `current`, or `None` in the brief window between `register()` and the first `update()`. Exists so `serialize_fn` can react to the transition (e.g. rendering a cleared value differently from a never-set one) without the World keeping a full history — just one step back, consistent with the World being snapshot-based rather than event-sourced |

`register()` creates `current = WorldEntryVersion(id=1, value=None, timestamp=<register time>)` and `previous = None` — registration itself produces the entry's first version, not a version-less placeholder. Every `update()` shifts the old `current` into `previous` and builds a fresh `current`, with `id` one greater than the previous version's `id`, regardless of whether the new value is `None` or not.

### World API

The World is a **singleton** — one instance exists per process/run, and (for now) there's a single global World rather than any per-agent partitioning/nesting. It's accessed via a module-level `get_world()` accessor (lazily creating the shared instance on first call) rather than a classic `__new__`-overridden singleton class — the more idiomatic Python shape (cf. `logging.getLogger()`), and it avoids the gotcha where `__init__` re-runs on every direct `World()` call even when `__new__` returns the cached instance. Calling `World()` directly is discouraged by convention, not structurally prevented.

Internally, the World holds two parallel per-key stores: registration metadata (`WorldEntryConfig`) and live state (`WorldEntry`), both keyed by the plain string `key`. Keeping registration and live state apart means, e.g., the snapshot handed to listener/trigger callbacks (below) only ever needs to copy the small `WorldEntry`, never the callables living in `WorldEntryConfig`.

The World exposes the following API:

- `register(key, type, ...)` — registers a new entry: stores its `WorldEntryConfig` and creates its initial `WorldEntry` (`current` version `id=1`, `value=None`); can happen at any time, including mid-run. Generic over the declared type (see "Keys" above) — the one place in this API a type checker verifies anything about it. Returns nothing; the caller already has the `key` string it passed in
- `unregister(key: str)` — removes an entry entirely (its `WorldEntryConfig`, its `WorldEntry`, and any listeners registered for that key are all gone); never triggers an LLM call, even if the entry had `triggers_llm_call=True`
- `update(key: str, value: Any)` — shifts the entry's current version into `previous` and builds a new current version (new timestamp; `id` one greater than the previous version's, always — see `WorldEntryVersion` above), evaluates trigger conditions, and (currently) triggers an LLM call whenever `triggers_llm_call` is set and the condition passes. Validates `value` against the entry's declared `type` at runtime (`TypeError` on mismatch, `None` always exempt) — the check that actually enforces type safety here. Clearing a value (without unregistering) is just `update(key, None)` — there's no separate `delete`. Dispatches the trigger call and any listener callbacks in the background rather than waiting on them, so a slow callback (e.g. the trigger handler making an actual LLM call) never blocks the caller. The `WorldEntry` these callbacks receive is a snapshot taken at dispatch time, not a reference to the live, further-mutable entry — otherwise a fast follow-up `update()` on the same key could race with a still-running callback reading stale in-place fields. This snapshot is cheap and safe to take because `WorldEntryVersion` objects are immutable once created — only the outer `WorldEntry`'s `current`/`previous` references ever change
- `get(key: str) -> Any` — returns the current value stored for a key
- `get_entry(key: str) -> WorldEntry` — returns the entry's full current `WorldEntry` (both `current` and `previous` versions), not just the value — primarily so a caller can pass it to `render_entry` (below)
- `add_listener(key: str, callback: Callable[[WorldEntry], None])` / `remove_listener(key: str, callback)` — subscribe/unsubscribe a callback invoked whenever the entry at `key` is updated, dispatched in the background alongside the trigger handler (see `update()` above) rather than synchronously within `update()`. Because dispatch is fire-and-forget, an exception raised inside a listener (or the trigger handler) is **not** surfaced to `update()`'s caller — it currently fails silently. This is a known gap, to revisit once the project has a logging story
- `set_trigger_handler(handler: Callable[[WorldEntry], None] | None)` — sets the single handler invoked when an update triggers an LLM call; one handler for the entire World, receiving an entry for whatever key fired regardless of that key's declared type
- `render_entry(entry: WorldEntry, *, archival: bool = False) -> Content` — serializes a `WorldEntry` snapshot into the XML-style block described below as `Content` (parts), *regardless* of that entry's `include_in_prompt` — an explicit per-entry request bypasses the aggregate-prompt filter, since the caller (e.g. a trigger handler wanting just the entry that fired, rather than the whole World) is asking for this entry specifically. `archival=False` (default) uses `serialize_fn`; `archival=True` uses `archival_serialize_fn` (which itself falls back to `serialize_fn`). Takes the `WorldEntry` itself, not a key, so it renders exactly the snapshot the caller is holding (e.g. one already received via a listener/trigger-handler callback, or fetched via `get_entry`) rather than re-reading whatever the World's live state happens to be at render time — the two can otherwise diverge if another `update()` lands in between the caller obtaining the entry and rendering it
- `render_full_prompt() -> Content` — serializes all `include_in_prompt` entries into a single `Content`, ordered by timestamp, by calling `render_entry(entry)` (fresh) for each and concatenating the parts

`render_full_prompt()` is named to leave room for an alternative, incremental rendering path — see open question below; the name should not be assumed final until that's resolved. `render_entry(entry)` is a first building block for that path: a trigger handler can call it directly on the entry it was handed instead of re-rendering the whole World, without `World` itself having to pick which strategy is "right."

### Rendered entry format

Each entry — whether from `render_entry(entry)` or as part of `render_full_prompt()` — is wrapped in an XML-style tag, chosen because Claude tracks tag boundaries and attribute values reliably — both reading them and echoing them back precisely, which matters since the model may need to reference a `key`/`id` exactly (e.g. in a Command). Because rendering now yields `Content` (parts) rather than a string, the wrapper is expressed as `TextPart`s **bracketing** the serialized parts: an opening `TextPart` (`<entry ...>\n`), then the parts returned by the (fresh or archival) serialize function, then a closing `TextPart` (`\nUpdated: ...\n</entry>`). For a text-only entry this flattens to exactly the block below; for a multimodal one the image sits as its own part between the two text parts (the Agent's adapter may merge adjacent `TextPart`s when converting to provider blocks):

```
<entry key="user_profile" id="1">
Jane is logged in as an administrator, currently editing the billing page.
Updated: 2026-07-20T14:32:10Z
</entry>
```

- **Prefix** (opening tag attributes, in the opening `TextPart`): `key` and `id` — structured and unambiguous, cheap for the model to copy verbatim. `id` is always present: `register()` itself assigns `id=1` to an entry's initial (empty) version, so there is no "no version yet" state that would otherwise need special-casing out of the tag.
- **Content**: the untouched parts returned by `serialize_fn` (fresh) or `archival_serialize_fn` (archival).
- **Trailing line** (in the closing `TextPart`, after the content): a plain `Updated: <ISO 8601 timestamp>` line, deliberately not an attribute — visually separating stable identity (`key`/`id`, referenceable) from freshness (informational only), while staying structurally inside `<entry>...</entry>` so its association with this entry (and not a neighboring one) is unambiguous rather than relying on line ordering. The timestamp is always **absolute**, never relative phrasing ("updated 5s ago"): once text is sent to the LLM it's frozen, so a pre-rendered relative time would silently go stale as soon as that message sits in history (or a cached prompt prefix) longer than the phrasing implies. If recency framing is wanted, it's the model's job at inference time, informed by a small "current time" marker injected fresh outside the cached/stable part of the prompt on each call — not stored on the entry or persisted into history.

`render_full_prompt()` concatenates these blocks' parts, one per included entry (each produced by `render_entry(entry)`), in timestamp order, into a single `Content`.

## Open questions

1. **Concurrent trigger coalescing** — when multiple `triggers_llm_call` entries update within the same agent step, should each trigger its own LLM call immediately, or should updates be batched into a single LLM call right before the next turn? *(Currently: always trigger immediately.)* Leaning **no coalescing**: the Agent design ([agent.md](agent.md), "Concurrency & interruption") allows multiple concurrent LLM calls that are mutually aware via `agent:activity` World state and interrupt each other by explicit model decision, rather than the World batching triggers on their behalf. Not yet closed here since it's ultimately the Agent loop's call.
2. **Full vs. incremental serialization** — should each LLM call resend the fully re-serialized World (`render_full_prompt()`), or only the data that triggered the call (`render_entry(entry)`), layered on top of existing conversation history? Both will be tried empirically — `render_entry(entry)` now exists as the building block for the incremental path, but which strategy an Agent loop actually uses per trigger is still undecided.
3. **Stale-`id` handling** — what happens when something (e.g. a Command) references an `id` that no longer matches the entry's current `id`? Since `id` now advances on *every* `update()` — including a mere clear or a TTL reset, not only a genuinely new value — a stale reference becomes detectable after any change to the entry, not just a replacement. The World doesn't expose anything like `get_by_id(key, id)` to look up a specific historical version (it only ever keeps `current`/`previous`, never a full history); the actual mismatch-handling behavior is likely primarily a Commands-spec concern.
4. **Sync/thread dispatch vs. asyncio ownership** — the World is currently sync and thread-based: `update()` mutates under an `RLock` and dispatches listeners/trigger handler on a `ThreadPoolExecutor`, so it can be called from any thread (sensor/hardware/bookkeeping producers included). The Agent, which needs an asyncio event loop for cancellable async tools, bridges by owning the loop itself and having its sync trigger handler do `run_coroutine_threadsafe(...)` — the World stays untouched and loop-agnostic. The rejected alternative was for the World to own/take an event loop and dispatch coroutine callbacks directly (`loop.call_soon`/`create_task`), dropping the executor. That would be cleaner *if the entire app ran on a single loop with nothing ever touching the World from another thread*, but it would force all listeners to be coroutines, require a live loop for every `update()`, and couple the arg-less lazy `get_world()` accessor to asyncio-runtime lifecycle. Revisit if a single-loop, fully-async architecture (no cross-thread World producers) becomes the intended shape. *(Currently: World stays sync/thread-based; the Agent owns the loop and bridges.)*
