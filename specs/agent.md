# Agent

**Status:** Updated

## Purpose

The Agent is the reasoning loop that observes the World and acts on it. It is triggered by the World (by subscribing to the World's `on_trigger` Event — see "The shared event loop"), builds an LLM prompt from World state, runs inference against a configurable provider, executes **Commands** (see [commands.md](commands.md)), and delivers what the model addresses to its user — the body of a tag in its response text — to the application's output Command as it streams. It owns the conversation **history**; the World owns current **state**.

The v1 design is settled and shipped: the sections under "Settled" describe what the Agent does today (single-in-flight loop, trigger coalescing, Command execution as World state, config-driven provider construction). "Open questions" contains genuine unresolved choices, while "Future improvements" records directionally-decided post-v1 work such as reaction concurrency and streaming; neither section describes current behavior.

## Settled

### LangChain as a primitive, not a framework

The Agent uses LangChain for two things only: the **provider-agnostic chat model** abstraction and **tool schemas / binding** (the primitive WICA **Commands** are built on — see [commands.md](commands.md)). It does **not** use a prebuilt agent loop (LangGraph's `create_react_agent` or similar) — WICA already owns state (World) and history, and both current requirements (cancellation, Command execution as World state) and future seams (streaming, a pluggable output Command) require control of the loop. So the Agent hand-writes its control loop over LangChain's model + tool primitives.

LangChain is confined to the framework's model-facing edge: the Agent's adapter and model call, the `Command` wrapper that builds and holds the backing `BaseTool` (see [commands.md](commands.md)), and the `on_prompt` instrumentation Event that carries LangChain messages (surfaced by [wica.md](wica.md)). The World, `Content`, and the Input pattern are LangChain-free, and nothing anywhere depends on a specific *provider* SDK. The Agent owns the single adapter that converts WICA `Content` (see [content.md](content.md)) into provider message blocks and back.

### Provider-agnostic model, from config

The model is selected from configuration (provider + model name + params), via LangChain's `init_chat_model`-style construction. Switching providers is a config change, not a code change. It is backed by a small settings object (`AgentConfig`) constructed directly or parsed from a dictionary/JSON framework representation — see [config.md](config.md).

**`AgentConfig` is unresolved data; Agent construction is where its references resolve.** Whether created directly or parsed from a mapping/file, it holds `api_key`/`api_key_env` and `system_prompt`/`system_prompt_file` without reading the referenced env var or prompt file. **`Agent.__init__` takes the `AgentConfig` directly** and performs those reads at build: it calls `resolve_system_prompt(config)` (prompt-file read) and `build_chat_model(config)` (which calls `resolve_api_key(config)` — env-var read, `MissingEnvError` if unset — then constructs the LangChain model). Both resolvers are pure functions owned by [config.md](config.md); the Agent is just the consumer that invokes them — so an unset key env or unreadable prompt surfaces at `Agent(config)`, not during config creation. Config-driven construction *is* the constructor: one build path, which the `Wica` facade drives as `Agent(config.agent, world=…, …)` (see [wica.md](wica.md)). A deterministic model for tests is selected through config too, via the `fake` provider (see [fake-provider.md](fake-provider.md)).

**One additive seam: an optional `model=` override.** `Agent.__init__` accepts an optional `model: BaseChatModel | None` — when a bespoke model is passed, it's used verbatim instead of calling `build_chat_model` (the system prompt is still config-expressed). This is the raw-model injection seam: for a model no config can express, and what the Agent's own unit tests use to drive the loop over a fully-scripted double the scripted `fake` provider can't express (blocking model calls, arbitrary tool-call sequences). `Wica.init` deliberately does **not** surface it — the facade stays config-only; the override lives at the `Agent` layer for direct construction.

**Most providers construct via `init_chat_model`; `huggingface-hub` and `openai-chat-completions-compatible` are the exceptions.** `anthropic`, `openai`, `gemini`, `mistral` and other LangChain-supported providers are built by `init_chat_model(model, model_provider=<langchain id>, …)`, where the LangChain id is the provider value itself except for the two WICA renames: `gemini` → `google_genai`, `mistral` → `mistralai` (config surface and the rename table in [config.md](config.md), "Providers"). `huggingface-hub` — the Hugging Face Hub's serverless Inference Providers — takes a dedicated branch in `build_chat_model` that constructs `ChatHuggingFace(llm=HuggingFaceEndpoint(repo_id=model, provider=<hf_provider>, huggingfacehub_api_token=<resolved api_key>, …))`, with the chat model's inherited 512-token output cap removed unless `model_kwargs` sets `max_new_tokens` (see [config.md](config.md), "Providers") (config surface — the `hf_provider` field, the extras — in [config.md](config.md), "Providers"). Because this branch builds the model directly instead of going through `init_chat_model`, it also owns the kwarg mapping: the key that `resolve_api_key(config)` returns (from `api_key`/`api_key_env`) is forwarded as `huggingfacehub_api_token`, not the generic `api_key` the `init_chat_model` providers receive. It must **not** use `init_chat_model`'s builtin `huggingface` provider, which builds a *local `transformers` pipeline*: that path is a blocking, in-process generation call that cannot be cleanly interrupted if reaction cancellation is added later. WICA uses a **served** model only — hosted or self-hosted, never an in-process one. (Even the hosted path's cancellation quality depends on `langchain-huggingface` implementing a truly-async `_astream` — the Agent streams every call, see "Streaming the model call"; it does, as do the other four providers' integrations.)

`openai-chat-completions-compatible` — any server implementing OpenAI's Chat Completions API, the self-hosted route — takes the other dedicated branch: `ChatOpenAI(model=model, base_url=<base_url>, api_key=<resolved api_key, else a fixed placeholder>, stream_usage=True, **model_kwargs)`. It is built directly so it owns three things `init_chat_model` would get wrong for a non-OpenAI server: the address is the config's `base_url` field, the key never falls back to `OPENAI_API_KEY` (a placeholder instead, since the client refuses to start without one), and usage is reported on streamed calls. The history-budget `ConfigError` for a model with no known window names this provider's case: set `context_window` to the server's own context size. The server does the model-specific work (chat template, tool-call parsing); WICA sends no `tool_choice`, which several self-hosted servers ignore — one reason the model speaks through a tag in its text and not through a forced tool call (see "Output: tags in the model's text" and [config.md](config.md), "Providers").

This is still one adapter at the Agent's I/O boundary, not a leak upstream: the `huggingface-hub` and `openai-chat-completions-compatible` branches are just provider-construction details inside `build_chat_model`. Everything above the Agent stays provider-agnostic regardless of provider.

### Configurable system prompt

The Agent takes a system prompt from config, so the agent/robot's persona and behavior are customizable per deployment without code changes. The config may carry it inline (`system_prompt`) or as a file reference (`system_prompt_file`); `Agent.__init__` resolves the two to a single string via `resolve_system_prompt(config)` at build (see [config.md](config.md), "System prompt"), so the loop never sees the file indirection — internally it works with a plain resolved persona string.

### System prompt composition: persona + WICA runtime primer

The system prompt the model actually receives is **composed**: the developer's resolved **persona** (verbatim, above) followed by a WICA-authored **runtime primer**. So the prompt is no longer strictly verbatim — WICA appends a small, fixed preamble explaining how the runtime works. (This reverses the earlier "framework injects nothing" default: a persona alone cannot teach the model WICA's unusual interaction model, and leaving it implicit made the model misread observations and Command acknowledgements.)

The primer is **curated, not a data dump** — it includes only what changes how the model should *interpret the prompt or choose actions*, never runtime plumbing the model can't act on (coalescing, fresh/archival rendering, TTLs, the shared loop, history internals are all deliberately omitted — with one exception, the history-window clause below, which is included precisely because a bounded context changes how the model should read its prompt). It is composed in **five parts, in order** (the second, third and fifth only when configured):

1. **Perception + acting** (always). The user-role messages are *observations of current World state*, not a chat transcript; each `<entry>` block is one piece of current context (an input, a sensor reading, or the status of an action the model took). Tool calls are asynchronous **Commands**; the immediate `tool_result` only confirms **dispatch**, and the actual outcome arrives **later as a World observation** (the Command's entry going terminal — see "Rendering to messages" and [commands.md](commands.md)). The deferred-outcome line is the single most load-bearing one: WICA's fixed-ack `tool_result` is confusing without it. The part also states that **several tool calls in one response all start at once and run concurrently, in no guaranteed order**, so sequencing is the model's job: when one action must finish before another starts, issue the first and issue the next in a later step, once the first is observed complete. Without this line a model carries over the sequential-loop assumption common to agent frameworks (calls listed in order run in order) and issues dependent or conflicting actions in the same response, where WICA runs them at the same time (see "Concurrency and long-running Commands in v1").
2. **The history-window clause** (only when `history_reactions` or `history_budget` is set — see "History window" below). The context holds only the model's most recent reactions — the latest observations and what it said or did in response — not the whole interaction; older exchanges are gone, so the current observation is the authority on the present state of the World, and anything that must persist is carried by the entries it shows, not by memory of earlier turns. Without this line a model reads a truncated history as the *whole* conversation (and, for instance, greets a user it has been talking to for an hour as a newcomer, or treats a Command outcome whose dispatch was cut as an action it never took). With unbounded history (neither field set) the clause is absent: there is nothing to warn about, and the primer stays fixed for a given config.
3. **The output clause** (only when an output Command is set). How the model addresses its user: write inside the output Command's tag; only the text inside reaches the user, text outside is private. It gives the Command's description and its attributes with their allowed values, says the tag is **not a tool**, and explains what makes WICA's output unlike a chat reply: what the tag holds is delivered in the background as a command whose entry appears in the World, the model can be called again while it is still being delivered, and a new tag **replaces** the one still being delivered (see "Output: tags in the model's text"). The wording names no verb — no "speak", no "say" — because the output may be a voice, a chat bubble or a screen; the tag's name and the Command's description say which. With no output Command the clause says instead that nobody reads the model's text.
4. **The silence clause** (always). The model is not obliged to react to every observation and may write `<noop/>` as its whole response to do nothing; but it is written **conservatively** — a request, question, or anything addressed to the model *should* be answered, and `<noop/>` must not be used to skip an expected response (see "The agent may choose not to act").
5. **The continuation clause** (only with an output Command and `max_next_steps` other than `0`). The end of the model's own speech does not call it again; if something remains to be done once it has finished speaking, it writes a `<next>` note in the same response (see "Continuing after an output"). The example in the clause is deliberately neutral: an example naming one of the application's actions measurably biases models toward it.

**Why the output clause says how to reply.** Empirically (gpt-4o observed), a primer that explains observations and allows doing nothing but never says *how to reply* leads some models to treat a plain request as an ignorable observation. Stating the reply mechanism explicitly is what keeps direct requests answered.

Composition happens in `Agent.__init__` (the persona is resolved, then the parts are appended; the history-window clause is decided by config, so it never causes a recomposition) and is **recomposed only when the output Command is set or cleared** (`set_output_command` — see "Output wiring"), since that is what switches the output and continuation clauses. The resolved persona is kept so recomposition never re-reads the prompt file. In the intended flow — wire, then `start()` — the combined string is therefore fixed before the first step and stays fully in the cached deep prefix: the primer costs tokens once per prefix, not per step. (Changing the output Command mid-conversation is allowed but rebuilds the system message from the next step on, at the cost of the cached prefix.) The authoritative primer text lives in module constants. Whether an application can opt out of or customize the primer is an open question (deferred — see Open questions), not a v1 knob.

### The shared event loop

The Agent's Commands are cancellable async tasks, so the Agent runs on an asyncio event **loop**. That loop is **owned and run by the `Wica` facade** (in one daemon thread per running cycle) and **injected into both the Agent and the World** — one loop for the whole system (see [wica.md](wica.md), "Lifecycle"; [world.md](world.md), "The shared event loop"). The Agent's constructor takes the `loop`; it does not create or own a thread of its own, and `stop()` does not stop or close the loop (that's `Wica`'s job).

- **All task manipulation happens on the loop thread.** Trigger batching, reasoning-step start, and every Command task live on this one loop, so scheduling and Command cancellation are race-free without locks — the whole reason the loop exists.
- **`stop()` cancels Agent work; it does not wait for that work to finish normally.** It first unsubscribes from new World triggers, then cancels the coalescing timer and every Agent-owned trigger, reasoning, and Command task. Cancellation has the ordinary asyncio meaning: cooperative async work unwinds at its next `await`, while an underlying synchronous function already running in an executor cannot be killed (its eventual result is discarded — see [commands.md](commands.md), "Cancellation reaches the task, not always the work"). When `stop()` is called from outside the shared loop, it drains the canceled tasks before returning; this is required before an owned Wica stops its loop thread, otherwise pending tasks would be frozen and could resume during a later cycle. When called from the shared loop itself, `stop()` cannot block that loop and therefore returns after requesting cancellation; the tasks unwind on subsequent loop turns. This distinction is accepted lifecycle behavior, not a guarantee that application work has completed. `start()` reattaches one trigger subscription; both lifecycle methods are idempotent.
- **The Agent is just a subscriber to the World's trigger — no thread-to-loop bridge.** The Agent subscribes to the World's `on_trigger` Event (see [world.md](world.md), "The trigger — the `on_trigger` Event"), attaching a one-line **sync shim** that schedules its async work: `world.on_trigger.subscribe(lambda e: self._loop.create_task(self._handle_trigger(e)))`. The World emits `on_trigger` on the loop thread (`call_soon_threadsafe`), so the shim runs there and `create_task` is safe — no `run_coroutine_threadsafe`. The shim is the whole bridge, and other observers can subscribe to the same raw signal alongside the Agent.
- **The World is handed the same loop**, rather than owning a `ThreadPoolExecutor` bridged to a separate Agent loop — this is what makes the system symmetric and single-owner. `update()` is still callable from any thread; the World hops to the loop via `call_soon_threadsafe` internally.

### History: re-renderable World snapshots, owned by the Agent

History is owned by the Agent, not the World (the World is snapshot-only — `current` + `previous` — and structurally can't hold a growing log).

- **History is an ordered list of WICA's own wrapper objects** over World snapshots (`WorldEntry`/`WorldEntryVersion` defensive copies, safe to retain independently of later World updates). The wrapper is ours (not raw LangChain messages) so we retain maximum data and convert to LangChain messages only at call time.
- **Messages are re-rendered from these objects on every LLM call**, not stored as frozen messages. Storing objects (not baked messages) is precisely what enables position-aware rendering (below).
- **Each step's snapshot is the full `include_in_prompt` World state, not just the entry that fired.** History holds one bundle per step (a coalesced burst of triggers runs one step and records one bundle — see "Trigger coalescing") — every currently-included `WorldEntry` (via the World's `get_prompt_entries()`), not only the one(s) whose update caused the step — so entries that are `include_in_prompt=True` but never themselves `triggers_llm_call` (passive context) still reach the model.

### History record shape

History is an ordered list of three record kinds:

| Record | Fields | Notes |
|---|---|---|
| Observation | `entries: list[ObservedEntry]` | Each `ObservedEntry` is the `WorldEntry` snapshot **plus the `serialize_fn` and `archival_serialize_fn` that governed it at observation time** (captured via `World.get_prompt_snapshot()`); history renders through these captured serializers, never through the World's live registration, so an observation renders identically after the key is unregistered or re-registered. Captures the full `include_in_prompt` bundle at step start, not just the entry that fired (see above) |
| Assistant text | `text: str` | The text of the model's response for a step **as the model wrote it**, output tags, `<noop/>` and `<next>` included — what was heard and what was private both render from it. Corrected once if an output is cut short: see "Output: tags in the model's text" |
| Command | `call_id: str`, `tool_call_id: str`, `name: str`, `args: dict[str, Any]` | Written at dispatch time, before the result is known — no `result` field here; the result surfaces later via a subsequent Observation record once the Command's World entry goes terminal, not by mutating this record. `tool_call_id` is the provider's id (used to reconstruct the native call) while `call_id` is the World-key suffix and `cancel_command` target, a short id WICA mints (`c1`, `c2`, … — see [commands.md](commands.md), "Command execution as a World entry") (code: `CommandRecord`) |

All three are immutable once created, with one exception: the assistant text of a response whose output is cancelled before its end is replaced by what was heard (see "Output: tags in the model's text"). History otherwise grows only at its tail — a Command record is never edited once its result is known. The only other mutation is the **history window** cutting whole reactions off the *head* (below); it never touches or reorders what it keeps.

**Rendering to messages.** A step's records render as: its Observation → a user message of `<entry>` blocks; then that step's Assistant-text + Command records → a **single** assistant message whose text is the response as written and whose `tool_calls` are the Commands issued as tool calls, rendered as the model's **native tool calls** (reconstructed from the neutral `CommandRecord` — see [commands.md](commands.md)); then one **`tool_result`** per call, carrying a **fixed acknowledgement** that points at the Command's World entry (`agent:command:<call_id>`) — **not** its outcome. An output has no tool call: it is in the assistant text, as its tag, and its execution shows in the Observations like any Command entry. Commands are deliberately **not** rendered as `"Calling foo…"` assistant *text* — a model shown its own actions as prose imitates it, emitting descriptions as free text instead of issuing real tool calls. **Consecutive Observations merge.** If two Observation records follow each other with no assistant-side record between them — the step's model call raised, exceeded its deadline, was cancelled by `stop()`, or returned neither text nor tool calls (an empty response, which counts as doing nothing) — the renderer emits them as **one** user message (the blocks of the older observation followed by the newer one's) rather than two consecutive user-role messages, which some providers' chat templates reject. Each observation keeps its own fresh/archival rendering (only the newest is fresh), so the merge changes nothing about prefix stability, and the older observation's content (which may hold the only record of a retired Command's outcome) is never dropped. **Omitted entries.** An observed entry whose captured serializer returns `[]` (see [world.md](world.md), "Omitting an entry") contributes no blocks — it is simply absent from that user message, fresh or archival alike, and since the decision depends only on the snapshot's values it keeps archival rendering a pure function of the snapshot (the caching invariant below). If *every* entry of an observation is omitted, the observation still renders as a user message, holding one fixed placeholder text block (`(no entries to observe)`), never an empty message: providers reject empty user content, and the first message after the system prompt must be a user turn. When such an observation merges into a preceding observation's user message (consecutive Observations, above) it contributes nothing and no placeholder is added; conversely, a placeholder left by an earlier all-omitted observation is replaced as soon as real blocks merge into that message.

A `tool_result` is pinned immediately after its `tool_use` (a `tool_use` can't be left dangling across turns), so it can only sit at the Command's *dispatch* site — not where the Command actually finished. Putting the outcome there would misplace it, and while a Command is still in flight a `tool_result` present at all reads as "the call returned." So the outcome is carried **not** by the `tool_result` but by the Command's World entry, rendered into the Observation like any other entry: `running` while in flight, terminal (`result`/`error`) at the step where the completion is observed — the causally-correct point. The `agent:command:<call_id>` entry is therefore **never skipped** (its serializer never returns `[]`). Command entries are registered with the Agent's own serializer, so the captured serializer already is that one — the renderer treats every observed entry uniformly and never inspects keys.

### Fresh vs. archival rendering

At each call the Agent renders the snapshot list → messages, applying a **freshness policy**: the newest observation is rendered **fresh** (rich, e.g. an image inline as `ImagePart`); older snapshots are rendered **archival** (light, e.g. a short text description). The mechanism lives in the World (`serialize_fn` vs. `archival_serialize_fn`, selected by `render_entry(entry, archival=...)` — see world.md); the **policy** (which entry counts as fresh) lives in the Agent.

Payoffs:
- Heavy multimodal data (images) is sent inline for exactly one turn, then downgraded to text — big token/cost savings for a multimodal robot.
- **Caching still holds.** Each snapshot flips fresh → archival exactly once, always at the tail (the previously-newest one); everything deeper is a pure function of an immutable snapshot, so it renders byte-identically every turn and the deep prefix stays cached. Only the last entry or two re-encode each turn — the same cost a normal growing conversation pays.
- Invariant to preserve: **archival rendering must be a pure function of that snapshot alone** — no "superseded by a later view" awareness, no reordering — or the deep prefix stops being cacheable.

Consequence: `render_full_prompt()` is **not** the Agent's path. The Agent has its own snapshot-history renderer (`snapshots -> list[BaseMessage]`) that is position-aware and multimodal. World rendering primitives (`render_entry`, the `Content` model) are the building blocks it composes; `render_full_prompt` remains a text/debug/full-current-state convenience.

### Prompt caching

A stable prefix is necessary, not sufficient: providers differ in what they do with it. OpenAI and Gemini cache a repeated prefix on their own. **Anthropic caches only at an explicit `cache_control` breakpoint**, and a read lands only where an earlier request wrote one, walking back at most 20 blocks. So with `provider: "anthropic"` the Agent marks **one breakpoint on the last block before the newest observation** — the deepest block the next request renders byte-identically, since the newest observation is re-rendered archival on the next step (a breakpoint after it would be written every step and never read). On the first step that block is the system prompt, which caches the tools ahead of it too; afterwards it is the previous step's last `tool_result` (or its text, for a text-only step), and the next step's breakpoint finds it one observation and one assistant turn later, well inside the lookback for an observation of a few entries.

- **A transport detail, applied after `on_prompt`.** `mark_cache_breakpoint(messages)` returns a copy with that block marked; `on_prompt` subscribers keep receiving the plain rendering, and history is never touched.
- **No knob.** Writing the cache costs a little more than plain input and every later step reads it at a fraction of the price, so a conversation always wins; an application that needs it off is an open question, not a v1 field.
- **Below a model's minimum cacheable prefix nothing is cached**, silently (the minimum varies by model — up to 4096 tokens on Haiku 4.5); the reported `cache_read_tokens` say whether it worked.

### History window

History is unbounded by default. `AgentConfig.history_reactions` (see [config.md](config.md)) bounds it to a number of **reactions**, so a long-running agent's prompt (and its process memory — every Observation retains full snapshots, images included) stops growing. Compaction and summarization remain future work (see Open questions); the window is the simple, lossy first strategy.

- **The unit is the reaction, and every reaction counts.** A reaction is one step, and every step appends exactly one Observation — whether it then produced text, Commands, a `<noop/>`, nothing, or failed at the model call — so a reaction is counted by its `ObservationRecord`, exactly as `on_reaction_ended` counts it. `history_reactions = X` guarantees the model always sees at least its last `X` reactions, the current one included.
- **The cut is hysteretic, not a sliding window.** Dropping the oldest reaction at *every* step would change the message right after the system prompt on every call, and the cacheable deep prefix (see "Fresh vs. archival rendering") would collapse to the system prompt alone. Instead the history is allowed to grow to **`2X`** reactions and is then cut back to the newest **`X`** in one go, so the prefix is byte-stable for `X` steps between cuts and each cut costs one prefix re-encode. `2X` is fixed, not a second knob.
- **The cut happens at step start**, right after the step's Observation is appended and before rendering: when the Observation count reaches `2X`, every record before the `X`-th-newest Observation is deleted from `self._history`. Cutting at an Observation boundary is always safe for the provider stream: the first message after the system prompt is a user turn, and a step's assistant message and its `tool_result`s stay together (they sit between two Observations). The records are **dropped from storage**, not merely hidden at render time — that is what bounds memory; the reaction history panel ([gradio-contrib.md](gradio-contrib.md)) already keeps each rendered prompt for anyone who wants to look back. A DEBUG log line reports each cut (reactions dropped, records dropped).
- **What is lost is lost.** The World holds *current* state and the history is the agent's only memory of past utterances and actions, so anything older than the window is gone for the model: an earlier instruction, a name, its own previous replies. That is the intended trade, and it has one design consequence for applications: **state that must outlive the window belongs in a World entry**, not in the conversation. A Command whose dispatch was cut while it was still running later shows its outcome as an `agent:command:<call_id>` entry the model never saw itself issue; the stream stays valid (the Command's `tool_call`/`tool_result` pair was cut together), `cancel_command` still works (the `call_id` is on screen), and the history-window primer clause tells the model such orphans can happen. A failed step's Observation that would have merged into the next one is cut like any other.
- **The model is told.** Because a bounded context changes how the model should read its prompt, the runtime primer carries a history-window clause whenever `history_reactions` or `history_budget` is set (see "System prompt composition"). Nothing else changes for the model: the newest Observation is still the fresh one, and every kept record renders exactly as before.

#### History budget: a usage-driven cut

`AgentConfig.history_budget` (see [config.md](config.md)) bounds the history by **tokens** rather than by reaction count: a fraction in `(0, 1]` of the model's context window that the prompt should stay under. It is a second, independent trigger for the same cut; the two policies compose (each cuts on its own condition), and either alone turns on the primer clause above.

- **The signal is the provider's own report, one step late.** Every successful model call returns the size of the prompt it just read — `TokenUsage.input_tokens` on the reaction record (see [instrumentation.md](instrumentation.md)) — exact, free, and available from every live provider. The Agent reads it right after the call. Counting tokens *before* each call is deliberately not used: for Anthropic it is a network round trip per reaction (a latency tax on a reactive loop), and elsewhere it is an offline approximation, with image tokens needing extra packages. A response without usage (a provider that reports none) simply never trips the budget.
- **The context window is resolved once, at build.** `AgentConfig.context_window` (tokens) when set; otherwise the model's LangChain **profile** (`BaseChatModel.profile["max_input_tokens"]`, a beta field auto-loaded from data bundled with the provider package — present for most Anthropic, OpenAI and Gemini models, absent for `huggingface-hub` and for models newer than the bundled data). The committed configs follow that split: the Anthropic, OpenAI and Mistral models resolve their window from the profile (200k / 128k / 128k), while the Gemini (`gemini-3.8-flash`, newer than the bundled data — 1,048,576 per the Gemini API) and Hub (`openai/gpt-oss-120b` on `cerebras`, 128k) configs set `context_window` explicitly. With `history_budget` set and neither source known, `Agent.__init__` raises `ConfigError` naming `context_window` as the fix — a misconfiguration is surfaced at build, never as a silently inert budget. `context_window` without `history_budget` is accepted and unused.
- **Two marks, one knob.** The **high-water mark** is `context_window × history_budget`; the **low-water mark** is half of it, fixed (the token-side twin of the fixed window's `2X` rule), so a cut is always followed by a stretch of byte-stable prefix rather than a cut at every step.
- **The cut.** When a call reports more input tokens than the high-water mark, the Agent drops, at the end of that step, the oldest reactions until the estimated prompt size is at or below the low-water mark — always keeping at least the current reaction, and always at an Observation boundary (the same `_cut_history` path as the fixed window: records dropped from storage, the step's own records untouched at the tail, a DEBUG log per cut).
- **The estimate separates the prompt's fixed part from its history.** A reported count is the **fixed part** (system prompt, tool schemas — often the bulk of a short session's prompt) plus one slice per reaction, so charging every reaction an equal share of the total would inflate the per-reaction cost and cut far too deep. Instead the Agent takes the **smallest count any call has reported** as the fixed part (the first call's: fixed part plus one reaction, a slight overestimate that errs toward keeping one reaction fewer), one reaction's cost as the rest of the current report spread over its other reactions, and keeps `⌊(low − fixed) / per_reaction⌋` reactions. It is still an estimate — the newest reaction (fresh, possibly with images) weighs more than an archival one, and a recomposed system prompt shifts the fixed part — but the low mark is a target, the high mark a trip-wire, and the next report corrects the course. When the fixed part alone leaves no room under the low mark, one reaction is kept and a WARNING says so: the budget cannot hold a stable band and needs a larger window or a shorter system prompt.
- **What the budget does not guarantee.** The signal lags one step, so a prompt can overshoot the high-water mark by about one reaction's worth before the cut lands; a budget well below `1` (say `0.5`–`0.7`) is what absorbs that. If the prompt nevertheless overflows the window, the provider rejects the call, the step ends as a `model_error` with no usage report, and the budget has nothing to react to — WICA does not parse provider errors to detect this case. The margin and, where it matters, a fixed `history_reactions` cap are the safeguards. A single reaction that alone exceeds the high-water mark cannot be cut and is logged at WARNING.

### Commands

The Agent's acting mechanism is **Commands** — WICA's unit of agent action on the World. Their concept, tool backing, execution-as-World-entry lifecycle, generic call description, and the deferred sync/async optimization are all specced in [commands.md](commands.md); this section covers only how the Agent *loop* uses them.

- Commands are registered easily — the Agent exposes `register_command(fn)` over LangChain's `@tool` / `bind_tools`, building the backing tool the model is bound to. `register_command` takes **one argument, `fn: Callable[..., Any] | Command`** (no `name`/`description` kwargs): a bare callable is auto-wrapped, a `Command` is used directly, and overriding name/description is expressed by passing `Command(fn, name=…, description=…)`. `Command` is the definition-time object that holds the backing `BaseTool`, keeping LangChain out of the command-definition surface (see [commands.md](commands.md), "The `Command` object"). Command names are unique and `noop`/`next`/`cancel_command` are reserved — see [commands.md](commands.md), "Names are unique and three are reserved".
- **The registered set is inspectable.** `agent.commands` is a read-only mapping `name → Command` of everything the model is bound to as a tool — application Commands and the auto-registered `cancel_command` once `start()` has attached it. The output Command is not among them (it is not a tool — see "Output: tags in the model's text"): `agent.output_command_name` is its name (`None` when no output Command is set). Through `Command.tool` a consumer reaches each Command's description and argument schema. This exists so a tool inspecting an Agent (a test harness describing the agent's action vocabulary, an observability panel) never has to read `_commands`; a consumer wanting only application actions filters out `cancel_command` by name.
- **Commands are used as-implemented.** The Agent must not require a backing tool to provide any WICA-specific hook (a describe/serialize function, a mode annotation, …). Off-the-shelf LangChain tools work unmodified (wrapped as `Command(tool)`). Anything WICA needs beyond `name`/`args`/`result` is optional and lives at the *registration/wrapper* layer — the `Command` — never inside the tool.
- Command execution is **async** and **cancellable** (asyncio tasks on the Agent's loop), tracked as a `agent:command:<call_id>` World entry whose value is a `CommandExecution` (see [commands.md](commands.md), "Command execution as a World entry"). A terminal execution triggers the next step. The durable history record of the *action* is the neutral `CommandRecord` (name/args/`call_id`); the *outcome* is the command-execution entry's own `CommandExecution` snapshot, captured in a later Observation. At render time the Agent reconstructs the native `tool_call` from the `CommandRecord`, pairs it with a **fixed-ack** `tool_result`, and lets the outcome render from the World-entry snapshot (see "History → Rendering to messages"); none of the provider-native blocks are stored.
- v1 always takes the uniform event-driven path for every Command; the inline fast-path for quick Commands is deferred (see [commands.md](commands.md), "Sync vs. async").
- The Agent **auto-registers one WICA-native control Command** (no app wiring): **`cancel_command(call_id)`** (see [commands.md](commands.md), "`cancel_command`"), which lets the model abort a Command it previously issued that is still `running` — an output included. It targets the command by its `call_id` — already on screen in the `<entry key="agent:command:<call_id>" …>` envelope, so no extra rendering — and reuses the Agent's existing loop-thread cancellation path (`Agent.cancel_command`; `stop()` cancels every Agent-owned task through the same loop-thread mechanism); an already-finished/unknown target is a harmless no-op. A future `cancel_reaction(reaction_id)` would cancel an in-flight reasoning reaction instead (see Future improvements).
- **Optionally, one application-supplied output Command** is set through `set_output_command(fn)` (see "Output: tags in the model's text", and "Output wiring" for the rules). The model issues it by writing its tag in the text, not by a tool call; its executions are otherwise ordinary Command executions.
- **Tool-calling support is not verified.** Because Commands *are* native tool calls, they only work against a provider/model that actually supports tool calling — universal on `openai`, but model-and-backend-dependent on `huggingface-hub`. WICA does **no** capability probe: a model that can't do tool calls either hard-rejects (a provider error surfaces from `ainvoke` — see the Agent-level errors open question) or silently emits no Commands. v1 relies on these runtime signals rather than pre-flight detection.

### Output: tags in the model's text

**The model addresses its user by writing a tag in its response text, and the tag's body is delivered to the application's output Command as it streams.** There is one output path. The application sets one output Command (`set_output_command` — see "Output wiring" below); the model is taught a tag of that name:

```
<say emotion="happy">Hello there!</say>
```

Only the text inside the tag is heard. Text outside it is the model's **private text**: nobody hears it, and it is reported on `on_private_text` (see "Instrumentation"). **With no output Command set, no tag is taught and all of a response's text is private** — an agent that only acts needs no output.

This replaces two earlier modes — free text delivered whole to an output sink, or the output Command issued as a forced tool call — and keeps what each was for. From the sink: the words stream, the first one reaches the application early, and nothing depends on `tool_choice` (which `mlx_lm.server` and Ollama ignore). From the Command: the output is a tracked, cancellable execution visible in the World, what is heard is separated from what is private, and an utterance can carry extra parameters. Measured on seven models, the tag form held or improved the live gate on six, started speaking 0.05 to 0.5 s earlier on short replies, and ended the runaway chains the forced tool call fed (`analysis/_text-output.md`, local notes).

**Three tags, owned by WICA.** The output Command's tag, and two fixed ones:

| Tag | Meaning |
|---|---|
| `<NAME attr="value">…</NAME>` | An **output**: `NAME` is the output Command's name, the attributes are its extra parameters, the body is what is delivered |
| `<noop/>` | Do nothing (see "The agent may choose not to act") |
| `<next>…</next>` | A private note of what remains to be done once the output is over; it asks for one more step (see "Continuing after an output" below) |

**The parser is lenient.** A response's text is parsed as it arrives, by one incremental parser (`wica.text_output`):

- **Text with no output tag at all is delivered whole**, as one output, when the response ends — so a model that forgets the tag is still heard (it is not streamed: until the response ends the parser cannot know no tag is coming). This applies only when an output Command is set, and not to a response whose text is a `<noop/>`.
- **A tag left open is closed by the end of the response.**
- **A `<noop/>` beside an output is ignored**; the output is delivered.
- **An attribute the output Command does not declare, or a value outside the ones it allows, is dropped** (logged at WARNING) and the parameter's default is used: the text is still delivered.
- **Any other `<…>` is ordinary text**, inside or outside an output.

**Each tag is its own output.** A response may hold several output tags; each is delivered as a separate output with its own attributes, **one after the other, in the order written** — `<say emotion="happy">Good news!</say><say emotion="sad">But there is a catch.</say>` is two outputs. The next one starts when the previous one has ended.

**An output is a Command execution.** In the reaction record an output counts as a Command (its `call_id` is in `command_call_ids`), `text_length` is the length of the response's text as written, and `first_output_at` is when the reaction's first output opened ([instrumentation.md](instrumentation.md)). When an output's first words arrive, the Agent opens its execution exactly like a Command's: an `agent:command:<call_id>` World entry (see [commands.md](commands.md), "Command execution as a World entry") holding a `CommandExecution` whose `name` is the output Command's and whose `args` are the output's attributes plus `text`, `running`, and a task that calls the output Command. So an output is visible to a later step while it runs, cancellable with `cancel_command`, traced, and reported on `on_command` / `on_command_ended` like any Command. What differs from a tool-call Command:

- **It starts before the response is complete**, and its `text` argument is filled as the model writes: the entry is written with an empty `text` when the output opens and again, with the whole text, when its body ends. `on_command` fires at that second moment.
- **Its entry shows what was written and how far delivery got**, never a call and never a tag: `say output (emotion="happy"): "Hello there!" — still being delivered, not finished`, then `— delivered`, `— cut off there, the rest was not delivered` or `— failed: …`. A call form (`Calling say(text=…)`) would contradict the prompt, which tells the model the output Command is not a tool. A tag form (`<say> "…"`) was tried and measured worse: shown its own outputs as tags in its observations, gpt-4o began writing its tools as tags too (`<functions.write_note …>`), failing the long-answer step 3 times in 12 against none in 12 with the form above. There is no verb, for the reason given under the output clause.
- **Its final state waits for the step that issued it.** A short output can end before the model has finished its response. Its terminal state is written only once that step is over, so its completion is never dropped by the single-in-flight loop and the step has decided whether it wakes a new one.
- **While it waits its turn it already shows as `running`.** The second output of a response is opened when its first words arrive, even if the first is still being delivered.
- **Whether its end wakes a step is readable.** `Agent.output_wakes(call_id)` returns whether the end of that output wakes a step (`None` for a call that is not an output), settled by the end of the step that issued it. It is kept while the output's entry exists and forgotten when a later step has observed and removed the entry (`None` again), so nothing grows with every utterance. A test harness waiting for the Agent to settle reads it ([wica-tester.md](wica-tester.md)).
- **It is not a tool.** The output Command is not bound to the model and is not in `agent.commands`; `agent.output_command_name` names it. A model that calls it as a tool anyway names an unknown Command (see "Response guards").

**The output Command receives the text as a stream or as a whole, by its signature.** Its first parameter is the text. Annotated `OutputStream` (exported from `wica`), it is handed the output as an async iterator of text pieces from the first word, and returns when the output is over — a voice can start speaking while the model is still writing. Annotated `str`, it is called once the output's body is complete, with the whole text. Its other parameters are the tag's attributes (see [commands.md](commands.md), "The output Command").

**One voice.** When a response starts an output, every output still running or waiting from an **earlier** response is cancelled: a new utterance replaces the one being delivered. So a model that answers "Stop, please." by saying "Okay, I'll stop" does stop — measured, weaker models answer an interruption by speaking and never call `cancel_command`, and explaining it in the primer did not change that. Only outputs are cancelled: a running `dance` or `write_note` is left alone, because speaking is not a request to stop acting, and the model has `cancel_command` for that. Outputs of the **same** response queue; they do not cancel each other.

**History keeps what the model wrote, then what was heard.** The response's text is recorded as written, tags included, as the step's assistant text (see "History record shape") — never as a tool call, which a model shown it would imitate. If an output is cancelled before its end, the record is corrected: that output's body is cut to what was delivered, and an output of the same response that never started is removed. What was delivered is what the output Command reports (`OutputStream.heard`); one that reports nothing keeps its whole text. So the model never believes it said what nobody heard.

#### Continuing after an output

**The end of an output wakes a step only when the model asked for it.** A model called again merely because it finished speaking has nothing to do, and weak models then speak again — and again: with a wake after every output, three of seven models chained utterances until stopped. So an output's completion does **not** trigger a step by itself. To continue, the model writes a note in the same response:

```
<say>Give me a moment.</say>
<next>look it up, then tell them what I found</next>
```

- **The note is private.** It is stored in the World entry `agent:next`, shown to the model in the step that follows as "You planned to do next: …", then cleared: a note is used once.
- **The note is the wake.** When the response's **last** output ends, a step runs. A response with a note and no output wakes nothing by itself: the note is shown at the next step, whatever triggers it.
- **Chained wakes are capped.** `AgentConfig.max_next_steps` (default `1`, see [config.md](config.md)) is how many steps in a row a note may wake before something other than the Agent's own output triggers a step. Past it the note is still shown at the next step, but the output's end wakes nothing (logged at WARNING). `0` turns the mechanism off: the primer does not teach `<next>` and no output ever wakes a step. `null` removes the cap.
- **A cancelled output wakes nothing**, note or not.

A Command issued as a tool call still wakes a step on completion according to its own `triggers_on_completion` ([commands.md](commands.md)): "speak and act together, then speak about the result" needs no note.

### Output wiring: `set_output_command`

The output Command is not a constructor argument: `Agent.__init__(config, *, world, loop, coalesce_window=0.2, model=None)` takes only what must exist at construction. It is wired afterwards, like Commands, through one setter (mirrored onto `Wica` — see [wica.md](wica.md), "Output wiring is delegated"). The reason is ordering: what an output Command references (a transcript, a UI, a TTS engine) usually needs the running system — the World for listeners, the `Event`s to subscribe — so it can only be built *after* the Agent exists.

- **`set_output_command(fn | Command | None)`.** A callable is wrapped as `Command(fn)`; a `Command` is used directly. It then, in order:
  1. **Validates, changing nothing on failure** — `ValueError` for a reserved name (`noop`, `next`, `cancel_command`), a name already registered as an application Command, a name that is not a valid tag name, a Command backed by an off-the-shelf tool, or a signature that cannot be an output's (see [commands.md](commands.md), "The output Command"). `register_command` keeps rejecting the current output Command's name, so the exclusion is symmetric whichever is wired first.
  2. **Records it** (`output_command_name` now returns its name) and **recomposes the system prompt** so the output clause teaches its tag (see "System prompt composition").
  `None` clears: `output_command_name` returns `None` and the prompt no longer teaches an output. An output of a replaced or cleared Command that is still running finishes (or is cancelled) normally.
- **Intended before `start()`; permitted while running.** A step already in flight keeps the output Command and the prompt it started with; the next step uses the new ones. The model binding is untouched: the output Command is not a tool.

### The agent may choose not to act

An observation does not oblige a reaction. The model declines by writing **`<noop/>` as its whole response**; a response with no text and no tool call counts the same. The step then ends with no World effect and no wake: the reaction record's `noop` flag is set (its outcome is `ok` for a `<noop/>`, `empty` for a response with nothing in it), nothing is dispatched, and no `on_command` fires. The `<noop/>` the model wrote is kept in history as that step's assistant text, so later context shows the choice; an empty response leaves no record, and its Observation renders merged with the next one.

Doing nothing is written in the text because speaking is. Measured with speech as a tag and `noop` left as a tool, every model was worse and three ran away: a model that speaks in one channel does not reliably reach for the other to stay silent. With both in the text, the four stronger models declined as reliably as they did with a forced `noop` tool call. `noop` is no longer a Command: the name stays reserved.

### Trigger coalescing

Perceptions often arrive in bursts — several Inputs updating within a few milliseconds (a speech event plus a proximity change, or a camera frame plus its detection). Firing one LLM call per trigger would waste calls, and under v1's single-in-flight loop it's worse than wasteful: the first trigger's step snapshots the World *before* the rest of the burst has landed, and the later triggers are then **dropped** as "busy" — their changes lost until some unrelated later trigger happens to fire. So the Agent coalesces a burst into one step.

- **A fixed leading-edge window.** The first trigger (when the Agent isn't already busy) opens a **coalescing window** — an `asyncio` timer on the loop thread, default **200 ms**, configurable via the Agent's `coalesce_window` (seconds). Triggers arriving while the window is open **join** it but do **not** extend it — so latency is bounded by the window and a fast stream can never starve the step (rejecting classic reset-on-each-trigger debounce for exactly that reason). When the window closes, **exactly one** step runs; because a step already snapshots the full `include_in_prompt` World (`get_prompt_entries()` — see "History"), every entry that changed during the window is observed together, for free.
- **`coalesce_window=0` disables it** — each trigger fires immediately, exactly the pre-coalescing behavior. This isn't a separate code path to reason about: a zero window is simply a window that closes at once.
- **Per-entry bypass.** An entry registered `bypass_coalescing=True` (see [world.md](world.md)) skips the wait: an update to it closes the current window **early**, running the step now and carrying along any triggers already collected in the window. For a stop/panic button or a barge-in utterance, the ~200 ms tax isn't worth paying. The Agent reads the flag off the `WorldEntry` snapshot the trigger handler is handed (it's carried there like `type` — see [world.md](world.md)).
- **Coalescing only batches the arrival burst *before* a step starts.** A trigger — bypass or not — arriving **while a step is already in flight** is still **dropped**, exactly as v1 does today (see "Concurrency and long-running Commands in v1" and "Future improvements"). Bypass skips the *window*, not the *in-flight drop*. Collecting triggers that arrive *during* a running step and coalescing them into a follow-up step belongs to the deferred reaction-concurrency design; the two compose but are separate.
- **All window manipulation happens on the loop thread.** The window timer is opened, joined, flushed, and cancelled only on the single shared event loop — the same invariant that makes cancellation race-free (see "The shared event loop"). The World schedules `_handle_trigger` onto that loop when a trigger fires; the window logic lives inside it.
- **`agent.on_trigger` fires once per collected trigger.** Even though a coalesced burst runs a single step, the Agent's `on_trigger` instrumentation Event fires **once for each trigger** that joined the window, so a consumer like the demo still shows every processed input on the conversation's input side (see Instrumentation). The other per-step artifacts — the Observation record, `on_prompt`, and the model call — happen **once** for the coalesced step. (This is the *filtered* trigger view — the World's `on_trigger`, which the Agent subscribes to, is the raw one that also fires for triggers dropped while busy.)

### Concurrency and long-running Commands in v1

The v1 Agent permits **one LLM reasoning call at a time**. While `_busy` is true, a new trigger is dropped and logged: it is not queued, added to history, or turned into a concurrent reaction. Trigger coalescing only batches the short arrival burst before a call begins.

Commands have a different lifetime. **All the Commands of one response dispatch at once:** the step creates one task per tool call, in the response's order, and ends; the tasks then run concurrently, with no ordering and no exclusivity between them — WICA neither serializes a response's Commands nor asks the provider to disable parallel tool use. A resource two Commands share (a speaker, a motor, a file) is therefore the application's to guard (a lock inside its Commands) or the model's to sequence across steps, which is what the runtime primer's concurrency line tells it to do (see "System prompt composition"; a per-response sequential dispatch mode or resource-exclusive Commands are possible future options, see [commands.md](commands.md) open question 2). Once a reasoning step dispatches its Commands, that step ends and the Agent becomes available even if one or more Commands are still running. A later input can therefore start a new reasoning step while a long Command continues in the background. The new step observes the Command's `agent:command:<call_id>` World entry as `running` and may issue `cancel_command(call_id)`. “Single in flight” refers to reasoning calls, not to Commands.

**Why at once, not one after another.** Three reasons, none of them a provider constraint:

- **It follows from asynchronous Commands.** A step dispatches its Commands and ends, so the Agent can react to a new input while a speech or a dance is still running, and cancel it. Running a response's calls one after another would need either a step that waits for its Commands — the Agent unavailable for as long as the slowest chain runs — or a per-response queue owned by WICA, a scheduler the design otherwise does without.
- **It fits the domain.** An embodied agent's actions are mostly independent and meant to overlap: speak while changing expression, speak while dancing, turn toward someone while greeting them. A sequential order would make the common case wait on the uncommon one.
- **Latency.** Independent actions start together; nothing waits on an action it does not depend on.

The price is that dependent actions issued together race: a cancel and a new call of the same Command, two Commands driving the same motor. WICA does not resolve that for the model; it tells it (the primer's concurrency line), leaves shared resources to the application, and lets the benchmark measure what models do (`no_colliding_cancel`, [benchmark.md](benchmark.md)). A per-response sequential mode or resource-exclusive Commands stay possible later, as additions.

Token streaming of an output is described under "Output: tags in the model's text"; `agent:reaction` World entries, concurrent reasoning calls, and model-issued `cancel_reaction` are future work described below.

### Model-call deadline

**Every model call has a deadline: `AgentConfig.model_timeout`, 10 seconds by default** (see [config.md](config.md)). The single-in-flight loop makes a hung call worse than slow: while it waits, every trigger is dropped, so the Agent stops hearing its inputs and the completions of its own Commands. Left to the providers, the wait is whatever their clients default to — ten minutes per attempt with retries on top for some, no bound at all for others — so the Agent bounds it itself rather than relying on per-provider transport settings.

- **One deadline over the whole call**, from the request to the stream's last chunk (see "Streaming the model call"), the provider's own retries included, enforced on the loop with `asyncio.timeout`. It is framework-level and provider-agnostic: no provider kwarg is set for it, and a transport timeout an application passes through `model_kwargs` still applies inside it (whichever is shorter fires first).
- **A deadline ends the step like a model error.** The call is cancelled, nothing is dispatched, the already-recorded Observation renders merged with the next one (see "Rendering to messages"), history stays well-formed and the Agent is free for the next trigger. It is logged at **ERROR**, and the reaction ends with its own outcome, `model_timeout` (not `model_error`), with `error` naming the deadline, so timeouts are countable apart from provider failures (see [instrumentation.md](instrumentation.md)). There is no retry: the next trigger is the retry.
- **The default is deliberately tight.** WICA targets reactive agents, where an answer later than a few seconds is already a failure; the measured model latencies of the benchmarked models sit well below 10 s at p95. An application running a slow reasoning model raises it; `null` removes it.
- **`stop()` is unaffected.** A cancellation from `stop()` still ends the reaction as `cancelled`: only the deadline's own expiry maps to `model_timeout`.
- **Cancellation reaches the provider only as far as its client is truly async.** For a model whose async path is LangChain's thread-pool fallback, the deadline frees the Agent at once but the abandoned request may finish in its thread; its result is discarded.

### Streaming the model call

**The Agent calls the model with `astream`.** Always, for every provider, with no config knob. The chunks are used in two ways. Their **text** is fed, as it arrives, to the output parser, which hands an output's words to the output Command before the response is complete (see "Output: tags in the model's text"). And they are **summed into one message**: everything else — the response guards, history, `on_private_text`, Command dispatch, a retry showing the rejected response — receives one complete `AIMessage`, exactly as from a non-streamed call.

**Why stream when nothing downstream sees the chunks.** A cancelled call — a `model_timeout`, `stop()`, `close()` — closes the connection either way; what differs is when the server notices. A streaming server writes every token, and the first write after the close fails, so every server stops within about a token. A non-streaming server writes nothing until it is done and stops only if it checks the connection on its own: measured, `llama-server` stops within about a second, while `mlx_lm.server` runs the abandoned generation to its output cap, sharing the GPU with the next reaction. Streaming makes cancellation reach the server on every self-hosted engine without per-server knowledge, and it is the transport that streaming output, a first-token measure, an idle deadline and model-call interruption all need. On a hosted provider an abandoned call costs a few tokens either way.

- **Chunks add up.** `AIMessageChunk`s sum with `+`: text concatenated, tool-call chunks merged by index, usage added, response metadata merged. The sum is converted to a plain `AIMessage`, its raw content kept as returned (an Anthropic thinking block included, so a retry can show it — see "Response guards").
- **Tool-call arguments are parsed strictly.** LangChain assembles a streamed tool call's arguments with a lenient JSON parser that closes what is left open, so a call cut by the output cap would come out as a valid call with truncated arguments — a `say` speaking half a sentence. The Agent parses each assembled call's raw arguments with a strict JSON parser instead: a call whose arguments are not one complete JSON object (empty counts as `{}`) is **malformed**. It is moved to the message's `invalid_tool_calls`, which is where a non-streamed call with the same arguments lands, and it is neither recorded nor dispatched; it is logged at **WARNING** with its name and the parse error. So a streamed and a non-streamed response with the same content are used the same way. The response guards see it as `ModelResponse.malformed`, and the default `incomplete_response` guard rejects the response and asks for the call again (see "Response guards").
- **Usage must be requested where a client does not stream it by default.** The Agent's token accounting (`history_budget`, the reaction record) reads the summed `usage_metadata`. The five hosted providers report it on a stream with their defaults (checked); the OpenAI client turns it off whenever a `base_url` is set, so the `openai-chat-completions-compatible` branch passes `stream_usage=True` (see "Provider-agnostic model, from config"). A server that ignores the request reports nothing: `usage` is `None`, as for any provider that reports none.
- **The first content is stamped.** The moment the first chunk carrying text or a tool call (its name or arguments) arrives is recorded as the reaction's `first_content_at` ([instrumentation.md](instrumentation.md)); a chunk holding only reasoning or metadata does not count. A model with no streaming path stamps it when its whole message arrives. The moment the first output opens — its first words handed to the output Command — is stamped apart, as `first_output_at`.
- **The deadline covers the whole stream.** A deadline, a `stop()`, or an error before the last chunk discards the partial message: nothing of it is used, and the reaction ends `model_timeout`, `cancelled` or `model_error` exactly as a non-streamed call would. A provider client retries a failed request, not a stream broken after it started, so an error mid-stream ends the reaction `model_error` at once; the next trigger is the retry.
- **A stream that yields nothing is a model error.** LangChain raises it as one.
- **A model without a streaming path still works.** LangChain's default `astream` falls back to the non-streamed call and yields its whole `AIMessage` once, which the Agent uses as is — the case for a bespoke model passed through `model=` that implements only `_agenerate`.

### Response guards

**A model's response is checked before anything uses it, and a rejected response is retried within the same reaction** — unless it has already started an output (see "A response that has started an output is not guarded" below). Between the model call returning and the response being used — its text to history and `on_private_text`; Commands to history and dispatch — the Agent runs its **response guards**. For a response that delivered nothing, nothing has reached the outside before that point, so a rejected attempt has no effect to undo: it is never recorded nor dispatched. Each guard either accepts the response or rejects it with feedback; on a rejection the Agent calls the model again, over the **same** rendered history plus a correction, up to `AgentConfig.max_retries` times (see [config.md](config.md)). Only the accepted response enters history; the rejected attempt and the correction never do, so later prompts read as if the model had answered right the first time.

This is part of the Agent's harness — the runtime around the model: a guard checks what the model *did* emit.

**What a guard is.** A callable taking a `ModelResponse` and returning `None` (accept) or a `Retry` (reject); it may be sync or async (an awaitable result is awaited, like a World listener's):

```python
@dataclass(frozen=True)
class ProposedCommand:
    name: str
    args: dict[str, Any]

@dataclass(frozen=True)
class MalformedCommand:
    name: str | None                         # the Command the call named, when it got that far
    raw_args: str                            # the arguments as the model wrote them
    error: str                               # why they could not be read

@dataclass(frozen=True)
class ModelResponse:
    text: str                                # the text as the model wrote it, "" when none (no output started: see below)
    commands: tuple[ProposedCommand, ...]    # every well-formed tool call, in order — cancel_command included
    bound: Mapping[str, Command]             # the Commands this call was bound to (= agent.commands at the step)
    malformed: tuple[MalformedCommand, ...] = ()   # tool calls whose arguments could not be read (see "Streaming the model call")
    truncated: bool = False                  # the provider stopped the response at its output cap (its stop reason: `max_tokens`, `length`)
    output_tokens: int | None = None         # the output tokens the provider reported; for a truncated response, the cap that was hit

@dataclass(frozen=True)
class Retry:
    feedback: str                            # told to the model: what was wrong, what to do instead
    show_response: bool = True               # retry showing the rejected response, or only a reminder
```

The view is neutral — no `AIMessage`, no provider ids, no `call_id` (none is minted before acceptance) — so guards stay LangChain-free like the command-definition surface ([commands.md](commands.md), "The `Command` object"). These types live in `wica.guards`, not in the `wica` namespace (see "Experimental" below).

**Who chooses the retry mode: the guard, per rejection.** The guard knows the error, so its `Retry` says how to retry:

- **`show_response=True` — show the rejected response and correct it.** For a concrete, fixable detail (a wrong argument, a missing call): the model sees what it did and fixes it. The retry prompt is the step's messages, then the rejected `AIMessage` as returned (its raw content, reasoning blocks included), then one `tool_result` per tool call it holds — a fixed "not executed: this response was rejected" — because a provider rejects a `tool_use` left without its result, then a user message carrying the feedback (in a fixed WICA frame: the previous response was rejected and nothing of it was executed; the feedback; respond again). A rejected response with neither text nor tool calls cannot be shown — providers reject an empty assistant message — and is retried as a reminder instead. So is a response holding a malformed tool call or cut at the output cap, whichever guard rejected it: a broken or cut response cannot be replayed to a provider.
- **`show_response=False` — a reminder, without the response.** For an error where seeing the response would pull the model back toward it (an over-long reply, forbidden content): the model writes a fresh answer. The feedback (in its own fixed frame: a previous attempt was rejected; the feedback) is appended as an extra text block to the **newest observation's user message** — not as a new user message, since two user turns in a row are what the renderer already merges for providers that reject them (see "Rendering to messages").

**Several guards, one decision.** All guards run on every attempt, in order — the default guards first, then the application's in the order they were added — so the feedback is complete. If any rejects, the attempt is rejected: the feedbacks are combined into one correction (one line each), shown with the response if **any** rejecting guard asked for it. A retry is built from the step's messages plus the **latest** rejection only, never a growing chain of failed attempts.

**Retries and their limits.**

- **One counter per reaction.** `max_retries` (default `1`) counts retries whichever guard rejected; the reaction makes at most `1 + max_retries` model calls.
- **Each attempt has its own deadline.** `model_timeout` bounds every model call, a retry's included (see "Model-call deadline"). A retry that fails or exceeds its deadline ends the reaction as `model_error`/`model_timeout`, exactly like a first call.
- **Out of retries: the reaction ends `rejected`.** Nothing is recorded but the Observation, nothing delivered nor dispatched — the same ending as a model error: the Observation renders merged into the next one, the Agent is free for the next trigger. Each rejected attempt is logged at **WARNING** with its feedback; running out is logged at **ERROR**. This is stricter than having no guards: with `max_retries: 0`, a response with one unknown Command used to dispatch its other Commands; now the whole response is rejected.
- **The busy time grows.** The single-in-flight loop holds the reaction through every attempt and every guard, and drops the triggers that arrive meanwhile (see "Concurrency and long-running Commands in v1"). A sync guard also runs on the loop thread itself and stalls everything on it (World updates, Commands, timers) while it runs: it must be a fast rule. An async guard (an LLM judging the answer) does not block the loop but holds the reaction for its whole duration; guard time is not under `model_timeout` and is recorded apart (see [instrumentation.md](instrumentation.md)).
- **A raising guard accepts.** A guard is application code; one that raises is logged at ERROR and counts as accepting, so a buggy guard cannot silence the agent.
- **The cache holds.** A retry adds messages only after the newest observation, so the Anthropic breakpoint before it (see "Prompt caching") is read, not rewritten.

**The default guards.** Three guards catch responses that break WICA's own rules, whatever the application. Each is an ordinary guard over `ModelResponse`, installed at Agent construction under its name:

| Guard | Rejects when | Retry |
|---|---|---|
| `incomplete_response` | the response did not arrive whole where it matters: a tool call's arguments could not be read (`malformed` is not empty), or the provider cut the response at its output cap (`truncated`) while it held a tool call — the last one is incomplete, however well-formed it looks | a reminder (a broken or cut response cannot be replayed); feedback says what was cut and that nothing was executed, and gives a length to stay under: half of where a malformed call's arguments stopped, or, for a truncated response, as many characters as the cap had tokens |
| `unknown_command` | a tool call names a Command that is not in `bound` | shows the response; feedback names the unknown Command and lists the bound ones |
| `invalid_args` | a tool call's arguments do not validate against its Command's argument schema (when the backing tool's `args_schema` is a pydantic model; a tool declaring a raw JSON schema is not checked). The last call of a truncated response is skipped: it is incomplete, not wrong | shows the response; feedback carries the validation error |

`incomplete_response` turns a call that used to vanish — dropped with a WARNING, the rest of the response used — or to be dispatched with whatever arguments survived, into a correction the model can act on; removing it restores that. Two signs are needed because providers return a cut call differently: OpenAI and Mistral return the arguments as far as they got, which makes the call malformed; Anthropic returns a well-formed call with empty arguments. The stop reason covers the second. The feedback's concrete limit matters: a bare "keep it short" did not make any model shorten. A cap too small for the model's reasoning cannot be recovered by a retry: the reaction ends `rejected`. Text cut at the cap is accepted — an output is delivered as far as it got. The next two catch, before dispatch, what used to surface only after it as a `failed` Command entry.

**A response that has started an output is not guarded.** The guards exist because nothing has reached the outside when they run. An output is delivered as it streams, so by the end of such a response part of it has been heard and cannot be taken back: the response is accepted as it is, and no guard runs. A malformed tool call beside it is dropped with its WARNING, and an unknown or invalid one is dispatched and ends as a `failed` entry the model then observes — what happened before guards existed. The guards therefore cover the responses that only act or do nothing. There is no guard requiring an output: the lenient parsing rules make a response's text heard whenever it has any (see "Output: tags in the model's text").

**Adding and removing guards.** `agent.add_response_guard(guard, *, name=None)` adds a guard (`name` defaults to the callable's `__name__`; a name already in use raises `ValueError`); `agent.remove_response_guard(name)` removes one, a default included (an unknown name raises `ValueError`); `agent.response_guards` is a read-only mapping `name → guard`, defaults included, in run order. Both are mirrored on `Wica` (see [wica.md](wica.md)). Like `register_command`, they are intended before `start()` and permitted while running: a step reads the guards once at its start, so a change takes effect at the next step.

**Experimental.** The guard mechanism is new and its right shape is still being learned. The default guards and their removal are supported; **`add_response_guard` and the `wica.guards` types are experimental** — they may change without a deprecation period, and the documentation describes them as such rather than recommending application guards yet.

**Instrumentation.** `on_prompt` fires once per reaction, with the messages of the first attempt — consumers match prompts to reactions one to one ([gradio-contrib.md](gradio-contrib.md)). Each rejected attempt instead emits `on_response_rejected` with a `ResponseRejection(attempt, response, feedback, show_response, will_retry)` — the attempt number (1 = the first call), the `ModelResponse`, the combined feedback, the mode and whether a retry follows. `on_private_text` and `on_command` fire only for the accepted response, so a transcript never shows a rejected one. The reaction record counts attempts, keeps each rejection's feedback, sums token usage over attempts and times the guards (see [instrumentation.md](instrumentation.md)). For the history budget the Agent reads the **first** attempt's `input_tokens`: a retry's prompt is larger than the history by the correction (see "History budget").

### Instrumentation: observability Events

The Agent exposes a small family of **`Event`s** (see [events.md](events.md)), all **instrumentation, not control flow**: subscribing changes nothing about what the loop does, and `Event.emit`'s per-subscriber isolation catches and logs a raising subscriber so it can neither abort a step nor starve sibling subscribers. Mutable payload data is defensively copied before emission, so a subscriber cannot rewrite the prompt sent to the model or the arguments stored/dispatched for a Command. They exist because the interesting moments of a step (what was sent, what fired it, what it decided to do) are otherwise internal to `_run_step`. The Agent **emits on them internally** at the right points — there is no separate hook-callback parameter and no `_fire_hook` guard; the Event *is* the seam, and any number of consumers subscribe.

| Event | Type | Emitted |
|---|---|---|
| `on_trigger` | `Event[WorldEntry]` | **once per trigger that a run-to-completion step observes**, with the World entry whose update caused it. A burst of *N* triggers coalesced into one step (see "Trigger coalescing") emits *N* times but runs a single step; a dropped single-in-flight trigger emits nothing. Includes command-completion re-triggers; a consumer that only cares about external inputs filters out `agent:command:*` keys itself. This is the **filtered** trigger view — distinct from the World's raw `on_trigger` the Agent subscribes to (see "The shared event loop") |
| `on_prompt` | `Event[list[BaseMessage]]` | with the exact rendered messages, immediately before the reaction's first model call — **once per reaction**; a retry's correction is reported by `on_response_rejected` (see "Response guards"). Fresh/archival rendering keeps the deep prefix byte-stable, so a subscriber logging every prompt sees the same cacheable prefix the provider does |
| `on_response_rejected` | `Event[ResponseRejection]` | once per attempt the response guards reject, before the retry (or the `rejected` ending) — see "Response guards" |
| `on_command` | `Event[CommandIssued]` | with **each** Command the model issues, when issued, as a `CommandIssued(name, args, call_id)` value (a small frozen dataclass carrying what a bare `(name, args)` tuple would, but named and evolvable). `call_id` is the WICA-owned id of this issuance — the `<call_id>` suffix of the Command's `agent:command:<call_id>` World entry and the target `cancel_command` takes (see [commands.md](commands.md), "Command execution as a World entry"). For a Command issued as a tool call the Event fires **after** that entry is registered and **before** its initial `running` value is written, so a subscriber may `world.add_listener(f"agent:command:{call_id}", …)` from inside the handler and then observe the entry's whole `running` → terminal life — the seam a test harness or a metrics sink uses to follow a Command it did not know the id of in advance. **An output** — one tag of the output Command — is reported the same way, once per tag, **when its body is complete**: `args` holds its attributes and its whole `text`, and its entry is by then already `running` (it was opened at the tag's first words; see "Output: tags in the model's text"). `cancel_command` is reported like any Command. A response that does nothing (`<noop/>`) issues no Command and emits nothing here: the reaction record's `noop` flag reports it |
| `on_private_text` | `Event[str]` | with the text the model wrote **outside** its output tags in a step, when non-empty, once the response is complete: its private notes, which nobody hears. With no output Command set, all of a response's text is private. The `<noop/>` and `<next>` tags are not part of it. `str` is immutable, so no defensive copy is needed |
| `on_reaction_ended` | `Event[ReactionTrace]` | once at the end of **every** reaction that started, whatever its outcome (ok/empty/model_error/model_timeout/rejected/cancelled) — the typed per-reaction latency/reactivity record. Emitted from the reaction's `finally`, after the Agent frees itself for the next trigger. See [instrumentation.md](instrumentation.md) ("Layer 1") for the record's fields |
| `on_trigger_dropped` | `Event[WorldEntry]` | once per trigger dropped because a reaction was already in flight — the counterpart of `on_trigger`, which only fires for triggers a reaction observed |
| `on_command_ended` | `Event[CommandTrace]` | once per dispatched Command when its terminal state is written, naming the reaction that issued it — the generic "any Command finished" signal (resolves open question 5 below) |

The first consumer is the conversation demo (see [conversation-demo.md](conversation-demo.md)): `on_prompt` feeds its prompt panel, `on_trigger` shows processed inputs on the conversation's input side, and `on_command` shows the robot's actions on the assistant side. They are equally plain debugging aids.

**The `Wica` facade surfaces these Events directly** (see [wica.md](wica.md)) — `wica.on_agent_trigger`, `wica.on_agent_prompt`, `wica.on_agent_command`, `wica.on_agent_private_text`, `wica.on_agent_reaction_ended`, `wica.on_agent_trigger_dropped`, `wica.on_agent_command_ended` *are* the Agent's Events, plus `wica.on_world_trigger` for the World's raw one. No adapters: because each is already an `Event`, `Wica` just re-exposes the object, and multiple consumers (demo panels, a logger, a metrics sink) subscribe to the same signal. `on_prompt` carrying `list[BaseMessage]` (a LangChain type) is natural here — the Agent *is* the framework's LangChain I/O boundary — and it does not leak into the `Event` primitive, which stays a pure project-agnostic leaf ([events.md](events.md)).

Alongside the reaction record, the loop opens OpenTelemetry spans for the same phases — `wica.agent.reaction` for the whole reaction, `wica.agent.model`/`wica.agent.command` nested under it — with context propagated from the triggering `wica.world.update` and, for a Command, into its task. See [instrumentation.md](instrumentation.md) ("Layer 2") for the full picture; nothing here changes what the model sees.

Complementing the hooks, the World and Agent **emit lifecycle logs** under the standard-library `wica.*` loggers, so the whole loop is traceable without wiring any hook. These levels describe **what the library emits**, not what is shown: WICA is a library, so it configures no handlers or levels (it installs only a `NullHandler` on the top-level `wica` logger) — the embedding application owns what surfaces, at what level, and where (see [config.md](config.md), "Logging is not framework config"). The emitted levels are: **DEBUG** for per-event detail (registrations, every World update and whether it triggered a call, trigger receipt, step start/complete, LLM output, command dispatch/start/end), **INFO** for coarse lifecycle (agent start/stop, dropped triggers), **WARNING** for command failures and for each response attempt the guards reject, and **ERROR** for a reasoning step whose model call raised or exceeded its deadline, for a reaction that ran out of retries (`rejected`), and for a response guard that raised. Listener and Event-subscriber exceptions are caught, logged, and isolated. A model-call failure or timeout ends the step (nothing is dispatched, the Agent is free for the next trigger, and the already-recorded Observation renders merged with the next one — see "Rendering to messages"); an output that had already started keeps what it received (see "Output: tags in the model's text"). A model-call failure is not yet represented in World state or history as something the model can see (see Open questions). Every Agent-owned task also carries a done-callback that logs any unexpected exception at ERROR, so no step or Command can fail silently.

## Open questions

These are genuine deferrals beyond v1, not descriptions of current behavior.

1. ~~**Output: explicit `speak` Command vs. free-text-as-speech.**~~ **Resolved** — one path: the model speaks by writing its output Command's tag in its text, and the tag's body is delivered to that Command as it streams (see "Output: tags in the model's text"). The earlier two modes (free text to a sink, or the output Command as a forced tool call) are gone.
2. **Configurable freshness policy.** The current policy is fixed: the newest Observation renders fresh and every older one archival. Whether applications need a configurable Agent-side renderer/policy is unresolved.
3. **Context-window growth.** ~~Append-only snapshot history needs an eventual truncation, compaction, or summarization strategy.~~ **Partially resolved** by the history window (see "History window"): `history_reactions` bounds history to the last `X` reactions with a hysteretic cut, and `history_budget` bounds it to a fraction of the model's context window from the provider's reported token usage. Whether a *lossless* strategy is also needed — compaction of archival observations, a summary record standing in for cut reactions, a model-driven memory Command — is still open; the window is deliberately the lossy, simple one.
4. **Agent-level errors as model-visible state.** Model-call failures are caught and logged at ERROR, the step ends cleanly, and history stays well-formed. What is still open is whether such a failure should be **represented to the model** — a World entry or history record it can observe, and a retry/backoff policy — the way Command failures already are via terminal `CommandExecution` state.
5. ~~**Generic command-activity listening.**~~ **Resolved by `on_command_ended`** — a listener subscribes once to learn when and how any Command ended (call_id, name, reaction_id, state), without a per-call `add_listener` or knowing the `call_id` in advance. See [instrumentation.md](instrumentation.md).
6. **Multiple agents.** Each `Wica` currently owns one Agent and one World. Partitioning one World across several Agents is not designed.
7. **Runtime-primer opt-out / customization.** WICA always appends its runtime primer to the persona (see "System prompt composition"). Whether an application can disable it (for a caller wanting full prompt control) or override its text is unresolved — the v1 primer is fixed, non-optional, and its wording lives in a module constant. A future `Agent`/`Wica` flag or override string is the likely shape if a need appears; deferred until one does.

## Future improvements (deferred out of v1)

The v1 implementation ships a reduced slice on purpose. These are already directionally decided — not open questions — but not yet built, so they don't get lost once v1 ships:

- **Full reaction concurrency and interruption.** A future design may publish each in-flight inference as an `agent:reaction:<reaction_id>` World entry, allow overlapping reasoning calls to observe one another, and expose a model-issued `cancel_reaction(reaction_id)`. It will need bounded concurrency and an atomic/single-owner output channel to prevent competing reactions from acting or speaking simultaneously. None of this exists in v1; `cancel_command` only cancels background Commands.
- **Sync/async Command optimization.** The inline fast-path for quick Commands (auto-by-latency or a registration flag — see [commands.md](commands.md), "Sync vs. async"). v1 always takes the async/event-driven path for every Command, per that spec's "default execution model" framing.
- **Live progress of an output.** An output's World entry is written when the output opens and again when its body is complete; it does not track the words as they are delivered. Writing live "currently saying: …" progress only matters once concurrent reasoning calls exist, so a competing call has something current to judge against.
- **Idle deadline.** A deadline on the gap between chunks ("no token for N seconds") beside the whole-call one would separate a slow model that is alive from a hung one. Not built: tool-call arguments still arrive in one burst on some providers (measured on a 200-word call: Anthropic and Mistral deliver them at the end, 3.9 s and 6.0 s with nothing in between), so a healthy call issuing a long Command would trip it. Text streams progressively on every provider measured. It does not help a cold model load either, where the wait is before the first token.
- **History compaction / summarization.** `self._history` is unbounded by default and bounded only by the lossy `history_reactions` / `history_budget` cuts (see "History window"); a lossless strategy (summary records, compaction) is not designed.
- **Agent-level errors as model-visible state.** Failures are logged and contained (see Instrumentation) but not yet represented in World state/history; Command failures are.
- **Multi-agent partitioning.** Still one `Agent` per one World.
